# Agentmeter — план

Локальный кросс-платформенный счётчик токенов для кодинг-агентов. Живёт в трее,
показывает кто сейчас работает, сколько осталось до лимита, какие сегодня были
задачи и — главное — куда именно утекли токены.

Всё считается из логов на диске. Никаких сетевых вызовов, ключей и телеметрии.

**Стек:** Electron + TypeScript + React, ядро парсинга — отдельный пакет.
**v1:** трей + лимиты + задачи дня. Деньги не считаем, только токены и % лимита.

---

## 1. Что лежит на диске

Разведка проведена на живой машине (macOS, Claude Code 2.1.226, Codex 0.145.0).
Объём: 590 транскриптов Claude (321 МБ), 327 роллаутов Codex (248 МБ).

### Claude Code

**`~/.claude/projects/<slug>/<sessionId>.jsonl`** — по строке на событие.

| запись | что даёт |
|---|---|
| `assistant` | `message.usage`: `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `cache_creation.ephemeral_1h/5m`, `server_tool_use.{web_search,web_fetch}_requests`, `service_tier` |
| | `message.model`, `requestId`, `timestamp`, `cwd`, `gitBranch`, `version`, `effort`, `sessionId` |
| | **`attributionSkill`** — токены запроса прямо привязаны к скиллу |
| | **`isSidechain`** — запрос сабагента, а не основной ветки |
| | `message.content[].tool_use` — какие тулы вызваны на этом шаге |
| `user` | `toolUseResult` — полный результат тула, `sourceToolAssistantUUID` — чей это ответ |
| `ai-title` | готовое человеческое название задачи («Отредактировать задачи для GARM проектов») |
| `last-prompt` | текст исходного промпта сессии |
| `attachment` | `deferred_tools_delta.addedNames` — какие тулы (в т.ч. MCP) подгрузились в промпт |
| `system` | `subtype: *_hook_summary` — `hookInfos[].command`, `durationMs`, `hookAdditionalContext` |
| `file-history-*` | какие файлы правились |

**`~/.claude/sessions/<pid>.json`** — живые сессии:
`{pid, sessionId, cwd, startedAt, version, entrypoint, kind, name}`.
`entrypoint` различает `cli` / `claude-vscode` / desktop / SDK — видно, откуда запущен агент.

**`~/.claude.json`** — `mcpServers` (глобальные и по проектам), `skillUsage`,
`projects[].{lastSessionMetrics, lastCost, lastModelUsage, lastTotal*Tokens}`.
**`~/.claude/stats-cache.json`** — дневная активность (сообщения, сессии, тул-коллы).
**`~/.claude/settings.json`** — хуки и разрешения.

### Codex

**`~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`**

| запись | что даёт |
|---|---|
| `session_meta` | `session_id`, `cwd`, `cli_version`, `originator` (`exec`/tui), `model_provider` |
| `turn_context` | `turn_id`, `cwd`, `approval_policy`, `sandbox_policy` |
| `event_msg/token_count` | `info.total_token_usage` и `last_token_usage`: `input`, `cached_input`, `cache_write`, `output`, **`reasoning_output`**, `total`; `model_context_window` |
| | **`rate_limits`**: `primary`/`secondary` с `used_percent`, `window_minutes`, `resets_at`, плюс `plan_type`, `credits` |
| `event_msg/task_started`, `task_complete` | границы хода |
| `event_msg/user_message` | текст задачи |
| `response_item/function_call` | имя тула и аргументы |
| `event_msg/mcp_tool_call_end` | `server`, `tool`, `duration`, `result` |

Две ловушки формата Codex, обе завышают расход в разы, если их не знать:
`token_count` пишется **дважды на один запрос** (повтор виден по неподвижному
`total_token_usage`), а `cached_input_tokens` — подмножество `input_tokens`,
а не добавка. Зато накопительный итог рядом с каждым запросом даёт встроенную
сверку, какой у Claude нет: сумма запросов обязана сойтись с ним до токена.
Компакт контекста Codex сообщает записями `compacted` и `context_compacted`.

### Дырка, которую надо закрыть честно

**У Claude локально нет данных о лимитах 5h/weekly.** В транскриптах их нет,
в конфигах тоже. Значит, окна считаем сами по своим же цифрам. Всё, что оценка,
в интерфейсе помечаем как оценку. У Codex наоборот — лимиты приходят точные,
прямо в логе.

Дописано по ходу: настоящий процент Claude всё-таки достаётся — из строки
состояния (1.9) и запросом к провайдеру (6.3), — и там, где провайдер ответил,
окно берётся у него целиком. **Потолок при этом не спрашивается у человека**:
он выражен во взвешенных токенах, объявленных тарифов в этих единицах нет, и
его решает та же калибровка, что и вес `cache_read` (7.4).

**Хвостовые прогревы Claude — измеренная поправка, а не точность.** После
последнего ответа сессии уходит от нуля до трёх служебных запросов, и следа в
логах они не оставляют: следующей записи, по разрыву кэша с которой их видно,
уже нет. Остаток после реконструкции — до 3.3% чтения кэша, всегда кратный
последнему префиксу. Решение зафиксировано в
[`roadmap/1.3-verify.md`](roadmap/1.3-verify.md): сессия, у которой хвост
непроверяем, показывается со знаком `≈`, а не выдаётся за точную. Зависимость
числа прогревов от времени жизни сессии измеряет вотчер в 2.1 — он и так знает,
когда сессия открылась и когда умер её pid.

## 2. Модель атрибуции — ядро продукта

Токены нельзя «поделить» задним числом по желанию: API считает целиком за запрос.
Но структура запросов позволяет разложить расход по двум осям.

### Ось A. Маржинальная стоимость (что добавили в промпт)

Для соседних запросов сессии:

```
cache_creation(N+1) ≈ output(N) + Σ tool_result(N) + текст юзера
⇒ стоимость результатов шага N = cache_creation(N+1) − output(N)
```

**Проверено на живой сессии** (`ollama-bar`, 5.2 МБ, 130+ запросов) — сходится.
При нескольких параллельных тул-коллах делим дельту пропорционально размеру
сериализованных `toolUseResult`.

Почему это лучше, чем просто мерить размер результата в логе: на реальном `Read`
результат в логе весил **382 КБ, а в промпт попало 2873 токена** — Claude Code
обрезал его перед отправкой. Дельта показывает то, что реально оплачено; размер
в логе — нет. Тот же механизм ловит скриншоты, у которых base64 в лог вообще не
пишется: картинку не видно, а её цену — видно.

Замеры маржинальной стоимости на той же сессии:

```
Bash    23 959 tok   93 вызова   ~257 tok/вызов
Read    19 257 tok   20 вызовов  ~962 tok/вызов
Edit     3 638 tok   45 вызовов   ~80 tok/вызов
```

Оговорки: компакт контекста ломает соседство (детектим по скачку и помечаем
отдельной статьёй расхода); дельта считается только внутри одной сессии.

### Ось B. Рекуррентная стоимость (что лежит в префиксе)

Всё, что попало в начало промпта, переплачивается **на каждом следующем запросе**
как `cache_read`. По деньгам это 10% ставки, но по **лимиту это полновесные токены**.
Отсюда самый неочевидный разрез: MCP-сервер, которым ты сегодня ни разу не
воспользовался, всё равно съел лимит — своими схемами тулов в системном промпте.

Считаем так: поднимаем сконфигурированные MCP-серверы, делаем `tools/list`,
токенизируем схемы → цена сервера за запрос. Умножаем на число запросов сессии.
Сверяем со стартовым `cache_creation` сессии (на этой машине — 28 113 токенов
до первого слова пользователя).

### Ось C. Прямая разметка

`attributionSkill` даёт скилл без всякой арифметики. `isSidechain` — сабагентов.
`mcp__server__tool` в имени тула — сервер. Хуки — из `hook_summary`.

## 4. Что честно не получится

- **Точные лимиты Claude из логов** — их там нет. Процент отдаёт сам провайдер:
  строке состояния (1.9) и по запросу (6.3); без этих источников окно
  показывается расходом без процента, и это помечено в интерфейсе.
- **Как именно `cache_read` весит в лимите подписки** — неизвестно. За сутки на этой
  машине: `out` 1.5M, `cache_write` 4.3M, `cache_read` 339M. Разница между
  «считать всё» и «не считать чтение кэша» — два порядка. Вес и потолок решаются
  вместе, линейной системой по наблюдениям провайдера (1.9), а не подбираются
  руками и не берутся из таблицы тарифов (7.4).
- **Локальная токенизация текста** приблизительна (±5%). Но она нужна только для
  дележа дельты между параллельными тул-коллами — сами суммы берутся из `usage`.
- **Разложение стартового оверхеда** до последнего токена: системный промпт
  Claude Code целиком нам недоступен, так что часть уйдёт в «прочее».

Сверено с каталогом выше. Первые два пункта помечены в v1, поэтому решаются
в коде поверх готовых компонентов; остальное — отдельным прогоном дизайна.
