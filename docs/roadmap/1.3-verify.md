# 1.3 — `agentmeter verify`, сверка с эталоном

**Кто:** сам · **Объём:** M · **Блокирует:** весь M1 ниже себя · **Ждёт:** 1.1, 0.6

Claude Code сам считает расход и пишет итоги в `~/.claude.json`. Это
независимый эталон: цифры получены не мной и не из моей арифметики. Пока мой
подсчёт с ним не сойдётся, всё остальное в проекте — красиво оформленная
неправда.

## Почему это блокирующий этап

Наивная агрегация проверена на 16 сессиях. **Не сошлась ни одна** — недобор
5–15% по чтению кэша, в разы по свежему вводу, доли процента по выводу. Такая
форма расхождения — не случайный баг, а недостающий класс запросов.

Класс найден. Ниже — что это и что от него осталось.

## Главное: часть запросов к API в транскрипт не пишется

Префикс запроса `N+1` обязан равняться префиксу `N` плюс то, что на `N`
записалось в кэш:

```
cr(N+1) == cr(N) + cw(N)
```

Где это равенство нарушено в большую сторону — между двумя соседними записями
прошёл запрос, которого в файле нет. Он дописал в кэш ответ ассистента и
прочитал весь префикс. Разрыв цепочки даёт его стоимость целиком:

```
прочитано  cr = cr(N) + cw(N)          весь префикс, полновесно по лимиту
записано   cw = размер разрыва          ровно out(N), ответ ассистента
```

Сигнатура запроса — большое чтение кэша, запись размером с ответ, вывод
порядка двух десятков токенов, ввод порядка полутысячи. Похоже на прогрев
кэша перед следующим ходом пользователя. Идёт примерно раз на ход, но не в
каждой сессии: в `callcenter` — 8 штук на 9 ходов, в `at` — ни одного на 20.

Проверка на `callcenter` сошлась **до токена**: восемь разрывов плюс один
хвостовой прогрев дают ровно недостающие 672 954 токена чтения и 13 111
записи.

## Второй класс: сабагенты, и почему эталон сам их недосчитывает

Сабагент пишет полный транскрипт, но не рядом с сессией, а внутрь неё:

```
~/.claude/projects/<slug>/<sessionId>/subagents/agent-<agentId>.jsonl
                                                agent-<agentId>.meta.json
```

`meta.json` даёт `agentType`, `description`, `toolUseId` и `spawnDepth` —
связь с родительским вызовом `Agent` прямая, гадать не нужно. Внутри —
обычные записи с `isSidechain: true`.

**Эталон этих файлов не читает.** В `lastModelUsage` попадает только
`toolUseResult.usage` вызова `Agent`, а это usage *последнего* запроса
сабагента. На `ollama-bar` разница: 212k чтения кэша по версии эталона против
**1.27M** по транскриптам самих сабагентов, вшестеро.

Отсюда следствие, которое надо принять до того, как писать `verify`: в части
сабагентов **наш подсчёт точнее эталона**, и подгонять его под эталон нельзя.
Сверка идёт по эталон-совместимому режиму, а показываем пользователю полный.

## Стриминг: первая строка ответа врёт по выводу

Строки одного `requestId` различаются: `output_tokens` в них растёт по мере
генерации, финальное значение приходит последним. Дедуп «взять первую строку»
теряет вывод — в транскриптах сабагентов, где ответ длинный, разница между
первой строкой и последней доходит до трёх порядков (4 токена против 6812).

Правило: схлопывать по `requestId`, беря **максимум** по каждому полю.

## Третий класс: Haiku

Служебные вызовы — заголовки сессий (`ai-title`), сводки «что было, пока вас
не было» (`system/away_summary`). В эталоне идут отдельной моделью с
`cacheRead = 0`, то есть чтения кэша не касаются. В транскрипте их нет,
восстановить нечем: видны только следы-результаты, не запросы.

Объём — десятки тысяч токенов ввода за сессию (`Projects`: 64 298 при 82 ходах
и 13 сводках). По выводу мелочь.

## Где мы сейчас

```bash
python3 scripts/probe/ground-truth-check.py            # с реконструкцией
python3 scripts/probe/ground-truth-check.py --naive    # как было
python3 scripts/probe/ground-truth-check.py --full     # + транскрипты сабагентов
```

| | сошлось точно | худшее расхождение по `cr` |
|---|---|---|
| наивно | 0 из 15 | −15% |
| с реконструкцией | 5 из 15 | ±3.3% |

Остаток — **хвостовые прогревы**: после последнего ответа сессии их уходит от
нуля до трёх, и следа они не оставляют, потому что следующего запроса уже нет.
Расхождение всегда кратно последнему префиксу: 0.00, 1.00, 1.00, 1.91, 2.01,
2.03 — то есть модель верна, неизвестно только число повторов. Корреляции с
паузой до последней записи, версией CLI и наличием `away_summary` не нашлось.

## Решение: принят исход «измеренная поправка»

Принято 9 августа 2026. Исходный критерий — 40 из 41 сессии до токена — снят,
и вот почему он недостижим в принципе, а не «пока не хватило усидчивости».

Число хвостовых прогревов зависит от того, сколько сессия простояла открытой
после последнего ответа. В логе этого нет: последняя запись — это последний
ответ, а не закрытие процесса. Даже если контролируемый эксперимент выведет
точное правило («прогрев на каждый истёкший 5-минутный TTL»), применить его к
**историческим** сессиям будет не к чему — время жизни процесса не записано
нигде. То есть эксперимент, поставленный сегодня, критерий всё равно не закроет.

Что зато закроет: вотчер живого слоя (2.1) видит и момент появления сессии, и
смерть её pid. Он даёт ту же зависимость даром, на сотнях сессий вместо трёх
ручных, и — что важнее — применимо: для сессий, прожитых при работающем
Agentmeter, хвост будет известен, а не смоделирован. Поэтому эксперимент не
отменён, а перенесён в 2.1.

Второй аргумент — порядок величин. Остаток здесь ≤ 3.3% чтения кэша, тогда как
**вес самого `cache_read` в лимите подписки неизвестен с точностью до двух
порядков** (1.9). Полировать 3% до того, как определён коэффициент, на который
эти токены умножаются, — заниматься не тем.

### Что это значит на практике

* Сессия, у которой хвост непроверяем, показывается со знаком `≈` — как и всё
  остальное, что оценка. Молча выдавать её за точную цифру нельзя.
* Сессии, сошедшиеся до токена (5 из 16), помечаются точными.
* Величина поправки известна и записана: до 3.3%, всегда в меньшую сторону,
  всегда кратна последнему префиксу сессии.

## Критерий готовности

```bash
node --experimental-strip-types scripts/probe/verify-live.ts
```

Зелёный, когда выполнены оба условия:

* ни одна сессия не расходится **больше чем на 3.5%** по чтению кэша, и каждое
  расхождение объяснено хвостовыми прогревами (кратно последнему префиксу);
* сессии без хвоста сходятся **точно, до токена** — сейчас таких 5 из 16.

Допуск здесь — не замазанное непонимание, а измеренная граница известного
явления. Разница в том, что причина названа, величина посчитана, а в интерфейсе
стоит `≈`.
