# 1.3 — `agentmeter verify`, сверка с эталоном

**Кто:** сам · **Объём:** M · **Блокирует:** весь M1 ниже себя · **Ждёт:** 1.1, 0.6

Claude Code сам считает расход и пишет итоги в `~/.claude.json`. Это
независимый эталон: цифры получены не мной и не из моей арифметики. Пока мой
подсчёт с ним не сойдётся, всё остальное в проекте — красиво оформленная
неправда.

## Почему это блокирующий этап

Наивная агрегация уже проверена вручную на 16 сессиях. **Не сошлась ни одна.**

```
проект at:      ждали (3566, 49358, 111151, 4824499)
                вышло (2331, 49231, 109868, 4562022)
проект mfc:     ждали (4993, 27827,  71590, 3040761)
                вышло (  76, 27785,  69986, 2783028)
                       ↑in    ↑out     ↑cw       ↑cr
```

Недобор систематический: 5–15% по чтению кэша, в разы по свежему вводу,
доли процента по выводу. Такая форма расхождения — не случайный баг, а
недостающий класс запросов.

## Файлы

```
создать:  packages/core/src/verify/*.ts
          apps/cli/src/commands/verify.ts
данные:   fixtures/ground-truth.json   ← слепок, только читать
```

## Что делает команда

Для каждой записи из `ground-truth.json`: находит файл сессии по `lastSessionId`,
считает суммы своим парсером, сравнивает с `lastModelUsage` — по каждой модели
отдельно, не только итог. Печатает таблицу расхождений и код возврата.

Разбивка по моделям важнее итога: она сразу показывает, чей это класс запросов.

## Критерий готовности

```bash
npm run verify
```

Зелёный, когда **≥ 40 из 41 проекта сходятся точно, до токена**. Не «± 2%» —
эталон точный, значит и сходиться обязано точно. Допуск здесь означал бы, что
я не понял данные, а замазал непонимание порогом.

## Что уже установлено

Разбивка по моделям из `lastModelUsage` разделяет расхождение на два разных,
и их надо расследовать порознь.

```
проект Projects (276 запросов)
  эталон  in=77605   out=268899  cw=472430  cr=99892677
  наше    in=999     out=260323  cw=464339  cr=86839161
    claude-haiku-4-5    in=64298   out=6951    cr=0
    claude-opus-5[1m]   in=13307   out=261948  cr=99892677
```

**Расхождение по свежему вводу — это Haiku.** 64 298 из 76 606 недобора
приходятся на модель, которой в транскрипте нет вообще. Чтение кэша у Haiku
нулевое, так что к недобору `cr` она отношения не имеет. Похоже на служебные
вызовы — генерация заголовков сессии и тому подобное. Объём приличный:
64 тысячи токенов ввода за сессию, то есть это десятки мелких запросов.

**Расхождение по чтению кэша — отдельная история**, целиком внутри Opus:
недобор 7–13% при том, что все `cr` в эталоне принадлежат Opus. Значит, часть
запросов основной модели в файл сессии не попала.

Правдоподобное объяснение второго: **сайдчейны сабагентов лежат отдельными
файлами** со своими `sessionId`, но в проектный итог входят. Косвенно
подтверждается тем, что у 25 из 41 записи эталона файл сессии на диске вообще
не нашёлся — файлов сессий заметно больше, чем «главных» сессий.

Гипотеза про `usage.iterations` **проверена и отпала**: на многоитерационных
запросах суммы по `iterations[]` и по верхнему уровню совпадают.

## Что проверять дальше

1. Связать сайдчейн-файлы с родительской сессией и пересчитать — закрывает ли
   это недобор `cr` полностью.
2. Найти, пишутся ли вызовы Haiku хоть куда-нибудь. Если нет — решить, считать
   их расходом пользователя или системным шумом, и отразить это честно.
3. Проверить ретраи: пишутся ли они с другим `requestId` или не пишутся вовсе.

## Если сойтись не удастся

Такой исход тоже возможен — часть расхода может быть принципиально не записана
в логи. Тогда результат этапа не «зелёный `verify`», а **измеренная и
задокументированная поправка**: известная доля, известная причина, оговорка в
интерфейсе. Что недопустимо — это молча показывать заниженные цифры, выдавая
их за точные.

Решение о том, какой из двух исходов принят, фиксируется здесь же и в
`docs/plan.md`, в разделе про честные ограничения.
