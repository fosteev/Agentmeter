# 7.3 — Окно первичной настройки

**Кто:** sonnet, high · **Объём:** L · **Блокирует:** ничего

Сегодня первый запуск выглядит так: приложение встаёт в трей и молча читает
логи. Человек не знает ни что нашлось, ни куда это уходит, ни сколько ждать.
Мастер (макет, раздел 11, строки 1807–2052) показывает найденное, спрашивает
пороги и поведение и говорит, сколько займёт индексирование. Сделать плохо здесь
значит завести второй набор настроек: экран, который спрашивает то, чего потом
нигде не изменить.

## По реальному коду (25 октября 2026)

**Чего в коде нет и что заводит этап:**

- **Флаг «мастер пройден»** — `setup.completed: boolean` в `DEFAULT_CONFIG`
  (`packages/core/src/config/types.ts`) со значением `false` и правилом в
  `config/validate.ts`. Миграция в `config/load.ts` рядом с `carryNotifyOnIdle`:
  файл конфига **есть**, а ключа нет — значит `true` (человек уже пользуется
  приложением, мастер ему не нужен). Нет файла — дефолт `false`, мастер
  показывается.
- **`setup:scan`** — новый вызов в `IPC_CALLS`: обход диска `discoverSources`
  по `claudeHome(cfg)` / `codexHome(cfg)` без индексации, ответ — по провайдеру
  путь, найден ли, число файлов, байты (`stat`), и модели из индекса
  (`SELECT DISTINCT sessions.provider, requests.model …`). `ConfigReport.sources`
  не годится: он считается из индекса и до первого прохода даёт нули.
- **`setup:open`** — открыть мастер повторно; зовётся кнопкой в разделе
  «Приложение» (`SettingsApp.tsx`) — это единственная правка `Settings*.tsx`.
- **`setup:finish { patch: DeepPartial<Config>; startup?: boolean }`** — пишет
  патч тем же `setConfig` (`main/config.ts:88`) плюс `setup.completed: true`,
  `startup` — через тот же код, что `startup:set`, закрывает окно мастера и
  открывает попап (тот сам покажет `PopupIndexing`, если проход не кончился).
  «Пропустить» — тот же вызов с пустым патчем и без `startup`.

## Контракт

Все значения мастера читаются и пишутся тем же конфигом, что и «Настройки» —
[`apps/desktop/src/main/config.ts`](../../apps/desktop/src/main/config.ts).
Ни одной настройки, которой нет в «Настройках» (таблица выше — полный список).

Значения на экране мастера — текущие из конфига (`config:get`), не дефолты
макета: при повторном открытии из настроек мастер показывает то, что выбрано.
Пишется всё **одним** патчем по «Начать» — пока человек листает шаги, конфиг не
меняется, и «Пропустить» на любом шаге оставляет его как был.

Модели на первом шаге приходят из разобранных логов, а не зашиты: чипы рисуются
по тому, что встретилось. Пока проход не дошёл ни до одного запроса — словами
«модели появятся после чтения логов», а не пустой строкой. Провайдер, у которого
логи не нашлись, — серая карточка «логи не найдены в …» с путём, где искали.

## Критерий готовности

```bash
npm test -w @agentmeter/desktop -- setup
npm test -w @agentmeter/core -- config
npm run check
npm run -w @agentmeter/desktop build && node --experimental-strip-types scripts/probe/desktop-smoke.ts
```

Тесты обязаны держать:

1. **«Пропустить» = дефолты.** Свежий конфиг → `setup:finish` с пустым патчем →
   файл равен `DEFAULT_CONFIG` с `setup.completed: true`; «Начать» с
   нетронутыми значениями даёт тот же файл байт в байт.
2. **Каждый контрол мастера пишет поле, которое правит раздел «Настроек»** —
   тест по списку: для каждого поля из патча мастера найден `Settings*.tsx`,
   который пишет тот же путь. Новый контрол без пары в настройках краснеет.
3. **Миграция:** конфиг без `setup` → `completed: true`; нет файла → `false`.
4. **Второй раз мастер не показывается**, но открывается `setup:open`.
5. **Мастер не блокирует индекс:** проход стартует до окна мастера и идёт, пока
   оно открыто (`openRuntime` не ждёт мастера); закрытое крестиком окно = «Пропустить».
6. Смоук (`--smoke`) создаёт окно мастера, грузит `setup.html` без ошибок
   консоли и закрывает.

Мутации, которые обязаны покраснеть: «Пропустить» пишет значения макета (92%)
вместо дефолта; мастер пишет поле сразу при щелчке, а не по «Начать»; миграция
ставит `false` существующему конфигу; контрол без пары в настройках; чипы моделей
зашиты списком.

## Подводные камни

- **«Пропустить» обязано давать дефолты конфига**, а не собственный набор:
  иначе у продукта два разных первых запуска, и воспроизводится жалоба только у
  одного из них. Отсюда же 75%, а не 92% макета.
- **Оценка времени индексирования — оценка.** Число берётся готовым из
  `IndexProgress.etaMs` (считает main) и помечается `≈`; своего расчёта по байтам
  в окне нет (правило 13). Пока `etaMs` нет — словами «оцениваем…», а не «0 с».
- **Мастер не блокирует трей.** Пока человек читает три шага, индекс уже
  собирается: закрытое окно мастера не должно означать потерянные полчаса.
- **Второй раз мастер не показывается**, но открывается из настроек — иначе
  единственный способ его перечитать это стереть конфиг.
- **Существующий пользователь мастера не видит.** Флаг в `DEFAULT_CONFIG` с
  `false` без миграции показал бы его каждому после обновления.
- **`setup.html` — в сборку приложения**, в отличие от `gallery.html`
  (`electron-builder.yml:52`); CSP — как у `window.html`.
- **`ELECTRON_RUN_AS_NODE`** (правило 11): смоук — только через
  `apps/desktop/scripts/launch.js`.
- **`t()` не на верхнем уровне модуля**; у кнопок и чипов — потолок длины в
  `i18n/limits.ts`: английский «Skip setup» и русский «пропустить настройку»
  разной длины, и вылезший перевод выдавит прогресс-полоски шапки.

**Решения (2026-10-25, по итогам сессии 7.3):**

*Раскладка.* Конфиг: `setup.completed` в `config/types.ts`, миграция
`carrySetupCompleted` в `config/load.ts` (файл есть, ключа нет — `true`; явное
`false` не трогается; файла нет — дефолт `false`). Правила в `validate.ts` нет:
у булева нет диапазона, тип проверяет обход (`typeMatches`), а тест держит
неверный тип. Контракт: `packages/ipc` — `SetupScan`, `SetupProviderScan`,
`SetupFinish`, три канала в `IpcCalls` и `IPC_CALLS`. Main: `main/setup.ts` —
`scanSetup`, `finishSetup`, `createSetupFlow` (порядок показа без Electron),
`createSetupWindow`; проводка в `main/index.ts` (`setupFlow`, окно в
`listeners()`, `showIfDue()` строго после `driveIngest`). Окно: `setup.html`,
`setup-main.tsx`, `renderer/setup.ts` (черновик, редьюсер, `SETUP_FIELDS`),
`components/Setup{Frame,ProviderCard,StepSources,StepThresholds,StepBehavior,Wizard}.tsx`.
Четвёртый вход в `vite.config.ts`; `setup.html` в `electron-builder` едет (исключён
только `gallery.html`), `package-smoke.ts` ждёт его внутри asar.

*Контракт каналов.* `setup:scan` (`void` → `{ providers: [{ provider, path, found,
files, bytes, models }] }`) — обход `discoverSources` по `claudeHome/projects` и
`codexHome/sessions` с `extra` из конфига (то, что проход действительно прочтёт),
`stat` на файл, модели — `SELECT DISTINCT` из индекса без `<synthetic>`; пока проход
не дошёл до запросов `models: []`, и окно пишет «модели появятся после чтения
логов». Окно перечитывает scan, пока проход идёт и сдвинулся (не чаще раза в 2 с), и
ещё раз, когда `indexing` исчез из снимка (последний кусок прохода событием не
объявляется). `setup:open` — поднимает окно (второго не бывает). `setup:finish
{ patch, startup? }` → `ConfigReport`: ключ `setup` из патча отбрасывается;
`limits.*.api.enabled` уходит **каналом согласия** (`setOauth`, чтобы выключение
стирало накопленный ответ), только если значение меняется; автозапуск — `setStartup`,
только если меняется; остальное и `setup: { completed: true }` — одним
`changeConfig` из `index.ts` (тема, `updates.auto`, событие `config:changed`).
«Пропустить» и крестик — тот же вызов с `{ patch: {} }`: файл = `DEFAULT_CONFIG`
плюс `setup.completed`. «Начать» с нетронутыми значениями даёт тот же файл байт в
байт и не пишет в «Объекты входа».

*Отступления от брифа и почему.*
- Кнопка «Открыть мастер» в `SettingsApp.tsx` зовёт `setup:open` через необязательный
  проп `onOpenSetup` с дефолтом на мост: так `SettingsTab.tsx` остался нетронутым
  (бриф разрешал одну правку `Settings*.tsx`). Цена — компонент знает про
  `window.agentmeter`; в тестах проп подменяется.
- Заголовок шага 2 — «Пороги и уведомления», а не «Планы и пороги»: про планы в нём
  больше нечего сказать (7.4).
- Тема в мастере **примеряется на самом окне** (`data-theme` по черновику) и не
  пишется в конфиг до «Начать»; иначе выбор «светлая» нельзя было бы оценить, а
  писать «по щелчку» запрещено.
- Попап после конца мастера открывается только при **первом** запуске (`due()` в
  момент открытия). Мастер, открытый из настроек, попап не зовёт: человек сидит в
  главном окне, а проход уже давно мог кончиться.
- Выход из приложения при открытом мастере пропуском **не считается** (иначе
  `before-quit` закрыл бы окна и засчитал решение, которого не было) — мастер
  вернётся при следующем запуске. Повторный запуск/клик по доку при открытом мастере
  поднимает мастер, а не главное окно.
- Чипов моделей не больше 8 на провайдера, остальное «+N» — карточка в 620 точек
  высоты не резиновая.
- Снятые контролы макета не верстались (список — в `design-implementation.md`, раздел
  11); остальные отступы шагов сверены с их блоками `SPEC_LINES` (рама 1813–1828 /
  1896–1903, заголовок 1832–1835, шаг 1 — 1830–1895, карточка 1839–1857 и 1876–1884,
  шаг 2 — 1926–1977, шаг 3 — 2008–2040). Ноль у невидимого `input[type=range]` — в
  `OFF_SPEC`, тот же довод, что у `SettingsAlerts`.
- Рама — `height: 100vh`, а не `100%`: у `body` высоты нет, подвал стоял под
  содержимым. Телам шагов добавлен `minHeight: 0` — без него тело росло за раму, и
  смоук, меряющий `scrollHeight` тела, был бы пустым.
- `remaining()` из `PopupIndexing.tsx` экспортирована (формат «≈ 40 с» один на попап
  и мастер, второй копии нет) — единственная правка в чужом компоненте, кроме

**Решения (2026-10-26, приёмка 7.3):**

- *Первый запуск решается по диску до открытия индекса* (`settleFirstRun` в
  `main/setup.ts`, вызов в `main()` перед `openRuntime`). Файл настроек пишется
  только правкой или закрытием главного окна, поэтому «нет `config.json`» не
  значит «новый человек»: живший одним попапом его не заводил, а индекс завёл.
  Нет файла, но индекс был — мастер не показывается (флаг в памяти, в файл
  уедет с первой правкой). Совсем новому `setup.completed: false` пишется в
  файл сразу — иначе индекс этого же запуска при следующем объявил бы его
  прежним, и мастер, брошенный выходом из приложения, не вернулся бы.
- *Битый JSON и `setup` не того типа — не первый запуск.* У исполнителя оба
  давали `completed: false`, и «Пропустить» или крестик записывали бы поверх
  файла давнего пользователя дефолты. Теперь мастер остаётся должен только при
  явном `false`; замечание обхода при этом остаётся.
- *`setup:finish` пишет только пути мастера* (`SETUP_CONFIG_PATHS`, тест держит
  его равным `SETUP_FIELDS` без автозапуска). У исполнителя канал брал любой
  `DeepPartial<Config>` и отбрасывал один `setup` — окно мастера могло записать
  этим входом каталоги логов или `statusline.previous`.
- *Попап после «Начать» открывается, когда окно мастера уже закрылось*, а не
  рядом с `close()`: закрытие последнего окна на macOS прячет иконку дока,
  приложение теряет фокус, и попап, открытый раньше, закрывался бы по `blur`.
  Порядок тот же, что у крестика; перед показом рассылается свежий снимок, как
  у щелчка по значку. Главное окно, закрытое при открытом мастере, док больше
  не прячет; установка обновления ставит `quitting` до `quitAndInstall` (тот
  закрывает окна раньше `before-quit`, и мастер засчитал бы «Пропустить»).
- *Смоук больше не ходит в живой индекс.* `desktop-smoke.ts` без явных
  `AGENTMETER_HOME`/`AGENTMETER_INDEX` заводит временный каталог под оба: первые
  пять прогонов исполнителя мигрировали живой индекс 11 → 13 и дописали
  `lifetimes.jsonl`.
- *Оставлено как есть (мелочи второго прохода):* черновик мастера, открытого из
  настроек, не слушает `config:changed` — правка в «Настройках» за время
  открытого мастера откатится его «Начать»; `setup:scan` каждые 2 с заново обходит
  каталоги (на живой машине — тысячи `stat`, терпимо); в тесте «нет ручек вне
  списка» не участвуют шаг 1 и рама — контролов в них нет.
