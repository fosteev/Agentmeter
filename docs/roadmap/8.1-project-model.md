# 8.1 — Клетка «проект × модель»: агрегат и контракт

**Кто:** сам · **Объём:** M · **Блокирует:** 8.2 (экран), 8.3 (CLI и бриф)

Всё, из чего состоит ответ, уже лежит в индексе: модель на каждом запросе,
проект на сессии, обе таблицы в развёртке соединены, плоская ось моделей
посчитана с 4.2. Нового ровно одно — группировка по двум ключам сразу и клетка
как самостоятельное число. Сделать это плохо можно единственным способом, зато
незаметно: группировка по двум ключам разъезжается с итогом периода молча —
сессия без проекта, запрос без модели, сабагент, попавший в обе клетки, — и
каждое отдельное число при этом остаётся настоящим. Поэтому сверка суммы клеток
с итогом здесь не приёмка, а часть самой функции.

## Контракт

**Сужение — только через `requestFilter(range, scope)`**
([`query/today.ts:100`](../../packages/core/src/query/today.ts#L100)). Свой
`WHERE` по периоду и провайдеру не писать ни одной строкой: разъехавшись с
лентой на один знак сравнения, он даст экран, где шапка и таблица считают разные
дни, и оба числа будут настоящими. Оттуда же `totalsFromRow`, `emptyTotals`,
`hasRequests`, `sourceCount`.

**Расход клетки — `input + output + cache_write + cache_read`**, ровно как в
`breakdownReport` ([`query/breakdown.ts:53`](../../packages/core/src/query/breakdown.ts#L53)).
Это та же величина, что `Σ (ctx + output)` из правила 16, записанная иначе;
второго способа считать расход в проекте нет и заводить его нельзя.

Тип — новый, плоский `BreakdownRow` не расширять (довод в «Что связывает руки
дальше» M8):

```ts
interface MatrixCell {
  model: string // как написано в логе: claude-opus-5, gpt-5.6-sol
  provider: Provider
  totals: Totals
  inherited: number // токенов пришло восстановленными запросами
}
interface MatrixRow {
  project: string
  totals: Totals
  cells: MatrixCell[] // по убыванию totals.total
}
interface SpendMatrix {
  rows: MatrixRow[] // по убыванию totals.total, без исключений
  models: MatrixCell[] // маргиналь по моделям за период
  totals: Totals
  emptyIndex: boolean
  emptyScope: boolean
}
```

`inherited` — не украшение и не процент: это токены клетки, пришедшие запросами
с `origin = 'reconstructed'`, у которых модель взята у соседа
([`claude/parse.ts:524`](../../packages/core/src/sources/claude/parse.ts#L524)).
Считать его долей в ядре нельзя — знаменатель у экрана и у CLI разный.

**Пустоты — три, как в правиле 15.** `emptyIndex` — `sourceCount(db) === 0`;
`emptyScope` — ноль запросов после сужения; «за период не работали» считается
`hasRequests(db, range)` **до** сужения. Вывести одно из другого по пустому
списку нельзя, и здесь это особенно наглядно: человек, оставивший фильтр на
Codex в клодовый день, иначе прочтёт «за неделю ничего», глядя на полную неделю.

## Критерий готовности

```bash
npm test -w packages/core -- matrix
node --experimental-strip-types scripts/probe/matrix-live.ts
```

Проба обязана печатать и проверять три равенства, падая на любом:
сумма `rows[].totals.total` = сумма `models[].totals.total` = `totals.total` =
итог `todayReport` за тот же период с тем же сужением. Совпадение «на глаз, в
пределах процента» здесь не годится: расхождение в 0.3% — это ровно потерянный
провайдер или задвоенный сабагент.

## Подводные камни

**`ambiguous column name: model` — первая же ошибка.** Колонка `model` есть и в
`requests`, и в `sessions`, поэтому в `GROUP BY` и `ORDER BY` имя таблицы
обязательно. Ловится сразу (SQLite отказывается выполнять запрос), но
подталкивает к худшему из решений — взять `sessions.model`.

**`sessions.model` — не модель запроса.** У сессии она одна, а по ходу работы
модель меняется: на живой машине 13 разных значений в `requests.model` и
проекты, где в одной сессии сменилось две. Матрица считается по `requests.model`
и только по ней.

**`<synthetic>` — значение модели, а не флаг.** В логе есть 7 запросов, у
которых `model` равно строке `<synthetic>`: их сочинил сам CLI (правило 10). В
таблицу они попадут моделью с таким именем. Отдельно от них существует **флаг**
`requests.synthetic`, который на живой машине совпадает с
`origin = 'reconstructed'` один в один (599 и 599, пересечение с `origin = 'log'`
пустое) и означает совсем другое. Одно слово, два смысла, соседние колонки —
перепутать их легко, а последствие тихое: `inherited` посчитается по модели с
именем, и клетка окажется точной там, где она оценка.

**Сессии без проекта есть, а запросов у них нет.** 29 сессий с `project = ''`,
и запросов на них ноль. То есть группировка по запросам такую строку не создаст
сама — и создавать её обходом по сессиям не надо. Если однажды такие запросы
появятся, строка обязана получить имя словами, а не остаться пустой ячейкой:
безымянная строка в таблице читается как поломка верстки, а не как факт.

**Моделей на длинном периоде не четыре, а тринадцать** — с хвостом в один-два
запроса (`claude-sonnet-5` — 4, `claude-haiku-4-5-20251001` — 1,
`qwen3.5-27b-32k` — 24). Маргиналь `models` не должна предполагать короткий
список: сортировка по убыванию обязательна, а решение, где резать хвост, — за
экраном, не за ядром.

**Сабагенты сворачивать нечем и не нужно.** В ленте есть `foldSubagents`, потому
что там строка — задача, и родитель с ребёнком дали бы одну тысячу токенов
дважды. Здесь строка — клетка, а клетка агрегирует **запросы**, каждый из
которых принадлежит ровно одной сессии. Добавить сюда сворачивание значит
сложить ребёнка с родителем руками.
