# 9.3 — Агрегат `workflowReport`

**Кто:** sonnet, max · **Объём:** M · **Блокирует:** 9.4, 9.5, 9.6

Одна функция ядра отвечает на все вопросы экрана: какие сессии — циклы, кто в
цикле сколько потратил и сколько написал, какая доля переделки в окне последних
N циклов и какой была в окне до него. Если этап сделать плохо, экран покажет
усреднённые по неделям доли. Discovery уже показал, что на малых выборках это
шум: неделя с двумя циклами дала 8%.

## Контракт

```ts
workflowReport(db: Db, opts: { config: Config['workflow']; scope?: RequestScope; until?: number }): WorkflowReport
```

- **Цикл** — корневая сессия (`is_sidechain = 0`), в дереве которой
  (`taskSessions`, `query/task.ts:79`) есть сабагент с ролью `executor` по
  `roleOf` из 9.2. Сортировка — по `started_at` корня. `until` — верхняя граница,
  нужна для тестов.
- **По циклу:** `spend` по ролям, включая `main` (корень) и `unknown`, по
  формуле `SPEND` (`query/matrix.ts:40`). Ещё `writes` по ролям — строки
  `tool_files`, где `action='write'`, по `session_id` узлов дерева. Плюс
  `writesAfter` по ролям (см. `rework` ниже), `toolCalls`, `toolErrors`
  (`is_error = 1`), `toolErrorsKnown` (`is_error IS NOT NULL`), вердикты ревьюеров — `verdictOf(last_text_head)`, и `inherited` (есть
  запросы с `origin != 'log'`).
- **Окно:** точки скользящего окна размера `config.window.cycles`. Значение
  точки — сумма числителей окна, делённая на сумму знаменателей. Показатели:
  - `rework` = writes.after / (writes.executor + writes.after), где `after` —
    `write`-записи всех узлов цикла, кроме исполнителей (корень, ревьюер,
    `unknown`…), с `requests.ts >= started_at` первого исполнителя цикла. По
    ролям `after` раскладывается отдельно (`afterByRole`), чтобы экран показал,
    кто переделывает: главная сессия (`/plan-review`) или ревьюер-агент;
  - `overhead` = (spend.main + spend.reviewer) / spend.executor;
  - `errorRate` — по окну `config.window.sessions` последних сессий (корни и
    сабагенты) из `scope`, знаменатель — только вызовы с известным `is_error`.

  Точка с нулевым знаменателем пропускается и не превращается в 0.

- **latest/prev:** последнее окно и окно **без пересечения** перед ним.
  `delta = latest - prev`. Если `prev` нет, дельты нет, а ответ говорит, сколько
  циклов есть (`count`).
- `scope.project` сужает корни, сабагенты идут за корнем. Пустая строка —
  законный ключ (`today.ts:100`).
- **Доли ролей** за все циклы окна, включая `unknown`. Экран обязан показать
  `unknown` и не прятать его.

**По реальному коду (9.1, приёмка 25 октября).** Контракт `errorRate` выше
остаётся как написан — знаменатель `count(is_error)`, вызовы с известным
статусом, — потому что приёмка 9.1 перенесла толкование в разбор: ключа
`is_error` нет — это `0`, а не `NULL` (правило 30 `CLAUDE.md`: в Messages API он
по умолчанию ложен, и Claude Code пишет явный `false` только у `Bash`, у
остальных ключ появляется лишь при ошибке). `NULL` теперь значит «не знаем» в
собственном смысле: у Codex (все вызовы), у вызова Claude без результата (1 на
44 823 за 30 дней) и у не булева ключа (0). Поэтому деление на известные
**само** отсекает Codex, и выбирать тут нечего: за 30 дней 966 ошибок на 44 822
известных = 2.155%, `discovery` — 2.153%. Для справки, раздельно: `Bash` 1.535%
(578 / 37 644), остальные 5.405% (388 / 7 178) — экрану это не нужно, но если
понадобится разбивка, считать её так же, `count(is_error)` в знаменателе.
Мутация 4 остаётся как написана и ловит деление на `count(*)`: в окне с
сессиями Codex доля разбавится их вызовами, у которых статуса нет ни у одного
(20 582 за всё время индекса), — эталон обязан держать такую сессию в окне.

**По реальному коду (9.2, 25 октября).** `roleOf(agentType, config.roles)` и
`verdictOf(last_text_head, config.verdicts)` уже есть (`workflow/roles.ts`, экспорт из
`@agentmeter/core`), `opts.config` — это `Config['workflow']`, поэтому `config.window.cycles`
выше верно как написано. Три вещи, которые нельзя угадать: (1) `roleOf` отвечает
`unknown` и на `agent_type = NULL`, так что **корневая сессия получает роль `main` по
`is_sidechain = 0` до вызова `roleOf`**; (2) пороги и цель — **доли 0..1**, а `overhead` —
кратность (`3` = втрое), в `WorkflowReport` показатели отдавать теми же единицами, чтобы 9.6
сравнивало `latest` с порогом без пересчёта; (3) `roleOf` не кэширует по сессиям, а кэширует
только скомпилированные шаблоны — звать его на каждый сабагент дерева дёшево.
Приёмка 9.2: `verdictOf` смотрит только **первую содержательную строку** головы — на
живом индексе это 14 accepted, 10 notes, 0 rejected, 11 none из 35 `review-opus`; эталон
`fixtures/workflow/` пусть держит ревьюера, у которого «не принят…» стоит в теле, а не в
первой строке (вердикт — по первой). `delta = latest - prev` — разность долей, экран
показывает её в п.п.

## Критерий готовности

```bash
npm run typecheck && npm run lint && npm test -w packages/core -- workflow && npm run fixtures:check
node --experimental-strip-types scripts/probe/workflow-live.ts
```

Мутации, каждая красная своим прогоном (записать в отчёт):

1. среднее долей вместо деления сумм;
   1a. правки главной сессии до запуска исполнителя (промт, roadmap) попадают в `after`;
2. окна с пересечением для `prev`;
3. `unknown` считается исполнителем;
4. ошибки делятся на все вызовы, а не на вызовы с известным `is_error`;
5. сабагент чужого проекта попадает в `scope.project`;
6. точка с нулевым знаменателем становится 0.

- Сабагенты воркфлоу: идентичность по имени файла (правило 4). Дерево — только
  через `parent_session_id`, без сравнения `sessionId` внутри файла.
- `taskSessions` защищён от циклов `UNION`. Не заменять на `UNION ALL`.
- Живых циклов с ролью по `agentType` сегодня мало: исполнители `exec-*`

  циклы пойдут после того, как `/plan` переключён на `exec-sonnet-high`
  (2026-10-25).

**Решения (2026-10-25, по итогам сессии 9.3):**

- **Раскладка.** Агрегат — [`query/workflow.ts`](../../packages/core/src/query/workflow.ts)
  (`workflowReport`, `WORKFLOW_ROLES`, `WorkflowOptions`), типы ответа — в
  [`query/types.ts`](../../packages/core/src/query/types.ts) (`WorkflowReport`,
  `WorkflowCycle`, `WorkflowSeries`, `WorkflowPoint`, `WorkflowVerdictPoint`,
  `WorkflowRoles`, `RoleNumbers`, `WorkflowNodeRole`), экспорт — `query/index.ts` и
  через него ядро. Формула расхода — **та самая** `SPEND`: у неё в
  [`query/matrix.ts`](../../packages/core/src/query/matrix.ts) добавлено `export`, второго
  экземпляра нет (правка вне списка «Файлов»). Дерево цикла — `taskSessions` (`UNION`),
  роли и вердикты — `roleOf`/`verdictOf` из 9.2. Эталон — `fixtures/workflow/`: 13
  корней Claude, 30 сабагентов и сессия Codex, README с расчётом каждой точки,
  `expected.json` (таблица `sessions` — входные данные расчёта, `cases` — восемь
  ответов); логи собирает `scripts/make-workflow-fixture.ts`. Вне списка брифа:
  `scripts/check-fixtures.ts` получил секцию workflow (21 сценарная проверка по сырым
  логам и 4 по арифметике: независимый пересчёт всех случаев `expected.json` из таблицы
  `sessions`), `scripts/probe/README.md` — строку про пробу. Тест —
  [`workflow.test.ts`](../../packages/core/test/query/workflow.test.ts), 47 проверок: эталон,
  ловушки поимённо, границы на индексе, собранном руками.
- **Форма ответа** (бриф её не называл). `workflowReport(db, { config, scope?, until? })`
  отдаёт `{ emptyIndex, emptyScope, cycles, rework, overhead, errorRate, verdicts,
  roles }`. `cycles` — все циклы под сужением по порядку `(started_at корня, id)`: у
  каждого `sessionId`, `project`, `startedAt`, `executorStartedAt`, `spend`, `writes`,
  `writesAfter` (шесть ролей, `main` и `unknown` всегда на месте), `toolCalls`,
  `toolErrors`, `toolErrorsKnown`, `verdicts[]`, `inherited`. Ряд — `WorkflowSeries`:
  `size`, `count` (сколько циклов или сессий есть), `points[]`, `latest`, `prev`,
  `delta`. Точка — `{ n, sessionId, startedAt, value, numerator, denominator,
  approximate }`: `n` — номер последнего элемента окна с единицы, `sessionId` — корень
  последнего цикла (для ошибок — последняя сессия), единицы те же, что у порогов 9.2
  (переделка и ошибки — доли 0..1, накладные — кратность). `roles` —
  `{ cycles, spend, writes, afterByRole }`: **суммы** по ролям за последние
  `min(size, count)` циклов, доли считает main (правило 13).
- **Где бриф молчал, и что принято.**
  1. **`latest` — окно, кончающееся на последнем элементе**; нулевой знаменатель — `null`,
     а не «последнее из существующих окон», как в `kpi_latest` у discovery: подпись
     «последние N циклов» над числом другого окна — молчаливая ложь. `prev` — окно,
     кончающееся на `size` раньше, если у него есть точка; `count ≥ 2·size` само по себе
     `prev` не гарантирует. Тесты: `latest` пуст при живом `prev` (синтетика).
  2. **Только полные окна:** 12 циклов при N = 5 дают 8 точек (`n = 5 … 12`), первые
     `size − 1` циклов точки не имеют.
  3. **`executorStartedAt` — старт первого исполнителя, у которого есть запрос.**
     Исполнитель без запросов начала не имеет (`started_at` у пустого файла — ноль), и
     мерить от него значило бы записать в `after` всё, что корень когда-либо сделал.
     Ни у одного нет — `null`, `after` нулевой. На живом индексе таких 0 из 38.
  4. **`until` — строго раньше, по началу корня.** Дерево берётся целиком: подчинённый,
     начавшийся позже `until`, остаётся в своём дереве, иначе граница резала бы цикл.
  5. **Порядок один везде — `(started_at, id)`**: циклы, сессии окна ошибок, вердикты
     ревьюеров цикла. При равной метке решает идентификатор, а не порядок вставки.
  6. **Сабагент идёт за корнем и в окне ошибок:** проект и провайдер сессии — корня.
     Сирота (родителя нет в индексе; на живом 0) — сама себе корень, как в ленте
     (`findRoot`). Цикл в `parent_session_id` обход не зацикливает.
  7. **Корень получает `main` до `roleOf`**; пользовательские правила ролей работают
     (тест: правило `general-purpose → executor` делает `b0` циклом).
  8. **`enabled` агрегат не читает** — вкладка и уведомления решаются выше.
  9. **Единица окна ошибок — сессия** (корень или сабагент по отдельности), как написано
     в брифе: «последних сессий (корни и сабагенты)». Не задача с вложенным деревом.
- **Скоуп — решения, меняющие объём (на подтверждение).**
  1. **Добавлен четвёртый ряд — `verdicts`** (в брифе три показателя окна). Макет 9.4
     просит «вердикты (доля «не принят» и «с оговорками») с маленькой линией», а 9.5
     запрещает пересчитывать окно в рендерере (правило 13) — без ряда из ядра линию
     нечем рисовать. Точка: числитель — с оговорками + не принят, знаменатель — принят
     + с оговорками + не принят («вердикта нет» не входит, как вызовы без статуса); в
     точке лежат счётчики всех четырёх вердиктов. Обратимо: ряд — один вызов `rolling` и
     одно поле ответа, остальные показатели его не читают.
  2. **Добавлен `emptyScope`** (правило 15): циклов после сужения нет, а без него есть —
     «фильтр отсёк всё» отличается от «ни одного исполнителя по вашим правилам»
     (`cycles.length === 0 && !emptyScope`). 9.4 этого четвёртого состояния не рисует.
  3. **Единица окна ошибок — сессия, и это стоит решить заново в 9.4.** На живом
     индексе 20 сессий — шесть часов работы и около 780 известных вызовов, а точек в
     ряду 1 369 (347 окон из 1 716 пропущены: в каждом двадцать сессий Codex подряд, ни
     одного известного статуса): экрану нужны последние несколько десятков. Замена
     единицы на задачу (корень с деревом) правится одной функцией — списком элементов
     перед `rolling`.
- **Находка на живых данных, которой нет в брифе: исполнители пишут через `Bash`.** В
  4 из 7 живых циклов (три от 6 октября, проекты pilot и pulse, и текущий) исполнители не
  оставили **ни одной** строки `write`: у них `Bash` 69 / 59 / 42 / 19 вызовов при
  `Edit`/`Write` ноль (проверено по сырому логу первого цикла: из 69 вызовов 17 — `python3 - <<'EOF'`
  с записью файла, 8 — `> файл`, 2 — `sed -i`; MCP-правки тоже не видны, правило 14), а ревьюер
  и главная сессия правят `Edit`-ом. Знаменатель переделки — записи исполнителя, поэтому
  такие циклы дают 100% (`ex 0 / after 5`), и окно с ними врёт вверх без единого
  исключения. Бриф кладёт эту поправку в подвал; число показывает, что одним подвалом
  не обойтись: данные для пометки уже в ответе (`cycles[].writes.executor === 0`),
  решение — за 9.4/9.5 (см. «По реальному коду (9.3)» там).
- **Мутации, все увиденные красными своим прогоном** (31: семь из брифа и 24 сверх). Бриф:
  1 среднее долей вместо деления сумм — 8 проверок; 1а правки корня до запуска
  исполнителя попадают в `after` — 10; 2 `prev` с пересечением — 8; 3 `unknown` —
  исполнитель — 16; 4 ошибки на все вызовы — 8; 5 сабагент чужого проекта попадает в
  `scope.project` (сужение по собственному каталогу) — 3, из них одна именованная на
  знаменатель (сумма по сессиям совпадает по счёту, различает только 88 против 92 известных
  вызовов); 6 нулевой знаменатель → 0 — 4. Сверх брифа: граница `>`; граница по
  последнему исполнителю; чтение считается записью; записи по разным файлам вместо строк;
  вердикт у всех сабагентов; «нет» в знаменателе вердиктов; `latest` — последнее
  существующее окно; расход без `cache_read`; окно по `id` вместо времени (циклы и
  сессии); `until` нестрогий; `project === ''` как «без сужения»; ничья без `id`;
  корень не `main`; вердикты цикла по `id` вместо старта; сироты выпадают; исполнитель без запросов задаёт границу; дерево не
  рекурсивное; цикл по любому узлу проекта; провайдер не сужает окно ошибок;
  `approximate` не выставляется; `emptyScope` без отличия от пустого сужения; роли по
  всем циклам; `UNION ALL` в `taskSessions` — **тест зависает** (бесконечная рекурсия в
  SQLite, красный по таймауту, а не по сообщению).
