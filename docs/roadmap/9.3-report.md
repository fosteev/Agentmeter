# 9.3 — Агрегат `workflowReport`

**Кто:** sonnet, max · **Объём:** M · **Блокирует:** 9.4, 9.5, 9.6

Одна функция ядра отвечает на все вопросы экрана: какие сессии — циклы, кто в
цикле сколько потратил и сколько написал, какая доля переделки в окне последних
N циклов и какой была в окне до него. Если этап сделать плохо, экран покажет
усреднённые по неделям доли. Discovery уже показал, что на малых выборках это
шум: неделя с двумя циклами дала 8%.

## Контракт

```ts
workflowReport(db: Db, opts: { config: Config['workflow']; scope?: RequestScope; until?: number }): WorkflowReport
```

- **Цикл** — корневая сессия (`is_sidechain = 0`), в дереве которой
  (`taskSessions`, `query/task.ts:79`) есть сабагент с ролью `executor` по
  `roleOf` из 9.2. Сортировка — по `started_at` корня. `until` — верхняя граница,
  нужна для тестов.
- **По циклу:** `spend` по ролям, включая `main` (корень) и `unknown`, по
  формуле `SPEND` (`query/matrix.ts:40`). Ещё `writes` по ролям — строки
  `tool_files`, где `action='write'`, по `session_id` узлов дерева. Плюс
  `writesAfter` по ролям (см. `rework` ниже), `toolCalls`, `toolErrors`
  (`is_error = 1`), `toolErrorsKnown` (`is_error IS NOT NULL`), вердикты ревьюеров — `verdictOf(last_text_head)`, и `inherited` (есть
  запросы с `origin != 'log'`).
- **Окно:** точки скользящего окна размера `config.window.cycles`. Значение
  точки — сумма числителей окна, делённая на сумму знаменателей. Показатели:
  - `rework` = writes.after / (writes.executor + writes.after), где `after` —
    `write`-записи всех узлов цикла, кроме исполнителей (корень, ревьюер,
    `unknown`…), с `requests.ts >= started_at` первого исполнителя цикла. По
    ролям `after` раскладывается отдельно (`afterByRole`), чтобы экран показал,
    кто переделывает: главная сессия (`/plan-review`) или ревьюер-агент;
  - `overhead` = (spend.main + spend.reviewer) / spend.executor;
  - `errorRate` — по окну `config.window.sessions` последних сессий (корни и
    сабагенты) из `scope`, знаменатель — только вызовы с известным `is_error`.

  Точка с нулевым знаменателем пропускается и не превращается в 0.

- **latest/prev:** последнее окно и окно **без пересечения** перед ним.
  `delta = latest - prev`. Если `prev` нет, дельты нет, а ответ говорит, сколько
  циклов есть (`count`).
- `scope.project` сужает корни, сабагенты идут за корнем. Пустая строка —
  законный ключ (`today.ts:100`).
- **Доли ролей** за все циклы окна, включая `unknown`. Экран обязан показать
  `unknown` и не прятать его.

**По реальному коду (9.1, приёмка 25 октября).** Контракт `errorRate` выше
остаётся как написан — знаменатель `count(is_error)`, вызовы с известным
статусом, — потому что приёмка 9.1 перенесла толкование в разбор: ключа
`is_error` нет — это `0`, а не `NULL` (правило 30 `CLAUDE.md`: в Messages API он
по умолчанию ложен, и Claude Code пишет явный `false` только у `Bash`, у
остальных ключ появляется лишь при ошибке). `NULL` теперь значит «не знаем» в
собственном смысле: у Codex (все вызовы), у вызова Claude без результата (1 на
44 823 за 30 дней) и у не булева ключа (0). Поэтому деление на известные
**само** отсекает Codex, и выбирать тут нечего: за 30 дней 966 ошибок на 44 822
известных = 2.155%, `discovery` — 2.153%. Для справки, раздельно: `Bash` 1.535%
(578 / 37 644), остальные 5.405% (388 / 7 178) — экрану это не нужно, но если
понадобится разбивка, считать её так же, `count(is_error)` в знаменателе.
Мутация 4 остаётся как написана и ловит деление на `count(*)`: в окне с
сессиями Codex доля разбавится их вызовами, у которых статуса нет ни у одного
(20 582 за всё время индекса), — эталон обязан держать такую сессию в окне.

## Критерий готовности

```bash
npm run typecheck && npm run lint && npm test -w packages/core -- workflow && npm run fixtures:check
node --experimental-strip-types scripts/probe/workflow-live.ts
```

Мутации, каждая красная своим прогоном (записать в отчёт):

1. среднее долей вместо деления сумм;
   1a. правки главной сессии до запуска исполнителя (промт, roadmap) попадают в `after`;
2. окна с пересечением для `prev`;
3. `unknown` считается исполнителем;
4. ошибки делятся на все вызовы, а не на вызовы с известным `is_error`;
5. сабагент чужого проекта попадает в `scope.project`;
6. точка с нулевым знаменателем становится 0.

## Данные

- Фикстура `fixtures/workflow/`: 3 проекта, 14 корней. Из них 12 циклов: у
  одного два исполнителя, у одного исполнитель и ревьюер с `general-purpose`
  (`unknown`). У двух циклов главная сессия правит файлы и до, и после
  исполнителя. Ещё 2 корня без исполнителя. У трёх ревьюеров вердикты: принят, с
  оговорками, не принят. Окно 5 → 8 точек. README — расчёт каждой точки руками.
- Эталон вне продукта: `~/Projects/discovery/sandbox/route-stats/dashboard/calcs.js`
  (`kpi_rolling`, `kpi_latest`). Логика окна та же, но роли там угаданы по промту,
  а переделка там считает только ревьюер-агентов, поэтому на живом индексе
  числа **не** обязаны сходиться. Сверка — только с
  фикстурой.

## Подводные камни

- Сабагенты воркфлоу: идентичность по имени файла (правило 4). Дерево — только
  через `parent_session_id`, без сравнения `sessionId` внутри файла.
- `taskSessions` защищён от циклов `UNION`. Не заменять на `UNION ALL`.
- Живых циклов с ролью по `agentType` сегодня мало: исполнители `exec-*`
  появились в 33 метах. Проба покажет «окно не набралось», и это правда. Новые
  циклы пойдут после того, как `/plan` переключён на `exec-sonnet-high`
  (2026-10-25).
