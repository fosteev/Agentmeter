# 1.8 — Лимиты: у Codex точные, у Claude оценочные

**Кто:** модель — сам, код — Codex · **Объём:** M · **Блокирует:** 1.9, 2.3, 2.5

Лимит — единственное число в интерфейсе, на которое человек смотрит, чтобы
принять решение прямо сейчас: продолжать или подождать сброса. Ошибка здесь не
портит статистику, а меняет поведение. Причём оба способа соврать уже
встречались в живых логах: показать недельный расход как пятичасовой (после
Codex CLI 0.145.0 они лежат в одном и том же слоте `primary`) и показать 1%
человеку, у которого 57% (протухшее наблюдение приезжает не по порядку).

## Контракт

`LimitWindow`, `LimitWindowKind`, `LimitObservation` и `LimitUsage` уже лежат в
[`packages/core/src/sources/types.ts`](../../packages/core/src/sources/types.ts)
и меняться не могут. Потолки плана и `cacheReadWeight` — в
[`packages/core/src/config/types.ts`](../../packages/core/src/config/types.ts),
поля уже есть, добавлять ничего не надо. `readLimits` в
`sources/codex/limits.ts` уже переписан и отдаёт `LimitObservation[]`.

Что должно появиться:

```ts
/** Наблюдения (из всех роллаутов сразу) → непересекающаяся цепочка окон. */
export function buildCodexWindows(observations: LimitObservation[]): LimitWindow[]

/** Запросы Claude (из всех сессий сразу) → окна с расходом. */
export function buildClaudeWindows(requests: Request[], limits: ClaudeLimits): LimitWindow[]

/** Окно каждого вида, открытое в момент `at`. Истёкшее — не текущее, а null. */
export function currentWindows(windows: LimitWindow[], at: number): Partial<Record<LimitWindowKind, LimitWindow>>
```

Окна собирает модуль `limits/`, а не разбор файла. Причина: окно живёт поперёк
файлов. Лимит общий на аккаунт, и одно пятичасовое окно разложено по всем
роллаутам, что шли в эти пять часов; собирать его внутри разбора одного файла
нельзя в принципе.

## Модель

**Окно — фиксированный интервал `[startsAt, resetsAt)` длиной `windowMinutes`,
открываемый первым запросом после истечения предыдущего.** Не скользящий:
внутри окна расход только растёт, в `resetsAt` обнуляется, следующий запрос —
когда бы он ни случился — открывает новое окно с новым якорем.

Пять правил, каждое из них поймано на живых данных:

1. **Вид окна — по длине, не по имени слота.** `300 → fiveHour`,
   `10080 → weekly`, `43200 → monthly`, прочее → `other` с сохранённым
   `windowMinutes`.
2. **Границы окна — от первого наблюдения.** Наблюдения одного окна относятся
   к нему, если `|startsAt − startsAt первого| ≤ max(120 с, 2% длины окна)`
   (6 минут для пятичасового). `startsAt`/`resetsAt` окна берутся от первого по
   времени наблюдения, дрожание последующих отбрасывается.
3. **Процент окна — максимум наблюдений, а не последнее.** `observedAt` —
   момент того наблюдения, которое дало максимум.
4. **Цепочка не пересекается.** Если приходит наблюдение с `startsAt` позже
   текущего окна и вне допуска, текущее окно закрывается, открывается новое.
   Ровно так же обрабатывается редкий случай, когда сервер сдвинул якорь
   посреди дня (см. подводные камни).
5. **Истёкшее окно не является текущим.** `currentWindows(w, at)` возвращает
   окно вида `k`, только если `startsAt ≤ at < resetsAt`; иначе для этого вида
   `undefined`. Показать 100% тому, у кого лимит уже сбросился, — та же ложь,
   что показать 1% при 57%.

**Claude.** Лимитов в его логах нет вовсе, проверено по всему `~/.claude`:
`sessions/*.json` содержит `cwd`, `entrypoint`, `kind`, `pid`, `sessionId`,
`startedAt`; `stats-cache.json` — счётчики сообщений, сессий и вызовов без
единого токена; в транскриптах записей о лимитах нет. Поэтому окна строятся из
наших же запросов по той же модели якоря, и `exact` у них всегда `false`.

```
weighted = input + cacheWrite + output + cacheReadWeight · cacheRead
usedPercent = weighted / cap · 100
```

Считаются **все** запросы, включая восстановленные (`origin: 'reconstructed'`),
сабагентские (`isSidechain`) и служебные (`synthetic`): это настоящие вызовы
API, и провайдер их посчитал. Ни одного фильтра по этим полям в `limits/` быть
не должно. В эталоне это проверяется в лоб: `claude-limits.jsonl` даёт 4
записанных запроса и 3 восстановленных по разрыву цепочки кэша, и суммы окон
посчитаны по всем семи. Фильтр по `origin` — единственный способ провалить
эталон незаметно: числа станут меньше ровно на то, чего в логе нет.

`usedPercent` = `null`, если `cap` = `null` или `cacheReadWeight` =
`null`; `weighted` = `null`, если `cacheReadWeight` = `null`. Ноль вместо
`null` здесь запрещён — это разные утверждения, и подстановка правдоподобного
веса вместо признания незнания есть ровно то враньё, ради борьбы с которым
продукт затевался.

## Критерий готовности

```bash
npm run check
npm run fixtures:check
node --experimental-strip-types scripts/probe/limits-live.ts
```

Проба на живых логах — шесть проверок, все обязаны быть ✓, иначе выход 1:

| # | проверка | порог | измерено разведкой |
| - | -------- | ----- | ------------------ |
| 1 | **Тождество с логом.** Каждое наблюдение из лога попадает ровно в одно наше окно того же `windowMinutes`, и `usedPercent` окна ≥ наблюдённого | 0 нарушений | — |
| 2 | **Якорь.** `\|startsAt − момент первого наблюдения окна\| ≤ 60 с` | ≥ 90% пятичасовых окон | 126/135 = 93.3%, медиана 10 с |
| 3 | **Монотонность.** Внутри окна процент не убывает | 0 падений | в сыром виде 68 (5 ч) и 41 (нед.) |
| 4 | **Цепочка.** Окна одного вида не пересекаются | 0 перекрытий | 1 из 134 до правила 4 |
| 5 | **Слоты не при чём.** В файлах CLI ≥ 0.145.0 окон вида `fiveHour` нет, все окна `weekly` | 0 `fiveHour` | 252 наблюдения новой раскладки |
| 6 | **Claude: покрытие.** Каждый запрос попадает ровно в одно окно каждого вида; сумма `usage` по окнам равна сумме по всем запросам | 0 расхождений, до токена | — |

Проверка 1 — это «совпадает с `rate_limits` в логе один в один» из роадмапа,
переписанное так, чтобы его можно было провалить. Сравнивать прочитанный из
лога процент с самим собой бессмысленно: сойдётся при любой ошибке. Провалить
можно другое — принадлежность наблюдения окну и то, что окно не занижает.

Проверки 2 и 5 — единственные здесь, где числитель не наш: якорь предсказывается
нашей моделью, а `resets_at` пишет провайдер, и разбор по имени слота ломает
проверку 5 мгновенно.

## Подводные камни

1. **`primary` сменил смысл.** До Codex CLI 0.145.0: `primary` = 300 мин,
   `secondary` = 10080. С 0.145.0: `primary` = 10080, `secondary` = `null`.
   На диске 14 716 наблюдений старой раскладки и 252 новой, ещё 36 с
   `primary` = 43200 (план `free`) и одно с `primary` = 0. Раскладка по имени
   слота показала бы недельный расход как пятичасовой — молча, без единой
   ошибки разбора.

2. **Наблюдения приезжают не по порядку.** `token_count` несёт снимок лимита из
   того ответа API, который его породил; при параллельных запросах ответ,
   ушедший раньше, может лечь в лог позже. В живых логах 68 падений процента в
   пятичасовых окнах и 41 в недельных, худшее — 57% → 1% на 33-й записи файла,
   а через 13 секунд снова 57%. Отсюда правило «максимум, а не последнее».

3. **`resets_at` дрожит.** У пятичасового окна разброс внутри одного окна до
   33 с (p90), у недельного обычно ≤ 1.4 мин. Но в трёх неделях из 28 он
   уехал на ~22 часа, а 2 июля якорь пятичасового окна сдвинулся на 52 минуты
   посреди дня (16:31 сообщает сброс в 18:32, 17:22 — в 19:24, тот же
   `limit_id`, тот же план). Правило 4 закрывает это: сдвинулся якорь — новое
   окно, а не расширение старого.

4. **Окно живёт поперёк файлов.** Лимит общий на аккаунт. Собирать окна внутри
   разбора одного роллаута нельзя: одно пятичасовое окно размазано по всем
   сессиям этих пяти часов, и каждая видит его кусок.

5. **Первое наблюдение сессии — не начало окна.** Медиана процента в первом
   наблюдении файла — 1 для пятичасового окна, но 112 из 307 первых записей
   имеют ≤ 1%, а остальные — сколько угодно. Якорь берётся из `resets_at`, а не
   из момента запуска сессии.

6. **`used_percent` целочисленный.** 96 уникальных значений на 14 716
   наблюдений, ни одного дробного. Отсюда квантование ±0.5 п.п. — любые
   производные величины (темп, прогноз до упора) на коротких интервалах
   бессмысленны, и в 2.3 это придётся помнить.

7. **Поля, которых не было раньше:** `credits`, `individual_limit`,
   `spend_control_reached`, `rate_limit_reached_type`, `limit_id`, `plan_type`.
   `limit_id` почти всегда `codex`, но встретилось три записи `premium`;
   `plan_type` — `plus`, `free` или `null`. В модель 1.8 они не входят, но
   разбор обязан их переживать, а `doctor` — показывать `plan_type`.

## Что дала разведка сверх задуманного

**Вес прочитанного из кэша в лимите подписки измерим — у Codex.** Процент от
провайдера, токены наши: подбором на 28 пятичасовых окнах одной модели
(`gpt-5.5`, ≥ 20 п.п. базы) метрика `fresh + k · cached + m · output` даёт
минимальный разброс при `k ≈ 0.2`; на недельных окнах той же модели `k = 0.2`
даёт CV 5% против 17% при `k = 0`. То есть **`cache_read` в лимите Codex
считается, но со скидкой примерно впятеро** — не «не считается» и не «считается
полностью».

Ни одна одиночная величина состав не объясняет: оценка бюджета по `total`
коррелирует с долей output на −0.85, по `output` — на +0.93, а по взвешенной
метрике — на 0.09, то есть состав перестаёт на неё влиять. Абсолютный бюджет
получается 12.2M взвешенных токенов на 100% пятичасового окна и 45.6M на
недельное, но он смещён вниз на весь расход, которого нет в наших роллаутах, и
модельнозависим (у `gpt-5.4` и `gpt-5.3-codex` подбор даёт другие числа на
худших данных).

В модель 1.8 это не заложено и не должно: у Codex процент приходит точным, а
переводить его в токены незачем. Значение находки в другом — это **первое
измерение того, как подписочный лимит вообще обходится с чтением кэша**, и оно
задаёт правдоподобный диапазон для 1.9, где тот же вопрос стоит по Claude и
пока отвечается «два порядка неопределённости». Ставить `0.2` в конфиг Claude
по аналогии нельзя: провайдер другой, тарификация другая, а 1.9 существует
именно ради ручной сверки с `/usage`.

**Границу дня разведка не закрывает.** Пятичасовое окно якорится на первом
запросе и потому спокойно ходит через полночь; `resets_at` приходит epoch-ом в
UTC. Ни то ни другое не отвечает на вопрос «что показывать в „сегодня“» — это
решение интерфейса, и живёт оно в `ui.dayStartsAtHour`. Открытый вопрос
остаётся открытым, но теперь он отделён от 1.8: окна лимита к календарным суткам
отношения не имеют вовсе.
