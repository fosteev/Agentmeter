# 1.5 — SQLite-индекс, дочитывание, вотчер

**Кто:** Codex · **Объём:** L · **Блокирует:** 1.6, 1.7, 1.8, 1.10, весь M2
**Ждёт:** 0.3, 1.1, 1.2, 1.4 — все готовы

Парсеры умеют превращать файл в `Session`/`Request`/`ToolCall`, но делают это
каждый раз с нуля и никуда не складывают. Индекс — то место, откуда все
последующие экраны берут цифры: пока его нет, ни `today`, ни трей, ни развёртка
существовать не могут.

Требование к результату ровно одно, и оно жёстче обычного: **индекс обязан
быть побитово равен тому, что вернули парсеры**. Не «примерно», не «с точностью
до округления» — до токена. Любая цифра, появившаяся или пропавшая по дороге из
парсера в базу, — это враньё в измерительном продукте, и поймать его потом
будет нечем, потому что сверять станет не с чем.

## Главное решение: единица дочитывания — файл, а не байтовый хвост

Изначально этап задумывался как чтение хвоста файла с сохранённого оффсета.
**Так делать не будем.** Замер на живых данных:

```
272 МБ, 591 транскрипт Claude   → 1.8 с    (≈150 МБ/с)
самый большой живой транскрипт  → 84 мс    (5.7 МБ, 325 запросов)
самый большой роллаут Codex     → 59 мс    (9.3 МБ, 473 запроса)
```

Перечитать изменившийся файл целиком стоит десятки миллисекунд — это укладывается
в критерий «дочит < 100 мс» с запасом. А чтение хвоста требует переносить между
чанками состояние парсера, и там ровно два места, где ошибка тихая:

- **Codex.** Дедупликация `token_count` держится на `lastTotal`. Начали чанк с
  чистого состояния — и пара дублей, разорванная границей, посчиталась дважды.
  Это тот самый двукратный завыш, который уже ловили в 1.2.
- **Claude.** Один `requestId` размазан по нескольким строкам `assistant`, и его
  надо схлопывать максимумом по каждому полю. Плюс реконструкция незаписанных
  запросов (1.3) и флаг `compacted` считаются **относительно предыдущего
  запроса** — на первом запросе нового чанка предыдущего нет, и разрыв цепочки
  кэша на границе просто не увидят.

Оба случая дают правдоподобные числа и зелёные тесты. Перечит файла целиком
убирает их не тестом, а конструкцией: состояния между вызовами не существует,
результат по определению тот же, что у `parseSessionFile`, который уже проверен
фикстурами, `verify-live` и прогоном по всему диску.

Отсюда следствия:

1. `parseSessionChunk` и `parseRolloutChunk` **удаляются** — из парсеров, из
   `packages/core/src/index.ts` и из тестов. Оставлять в публичном API функции,
   которые на границе чанка врут, нельзя: их подберёт 2.1 под «tail лога» и
   получит те же двойные счёты. Живому слою в 2.1 хватит перечита одного файла
   за 84 мс при бюджете в 2 с.
2. Тройка `(path, inode, offset)` из 0.3 остаётся и работает как задумана —
   меняется только то, что после обнаружения роста файл читается **с нуля**, а
   не с `offset`. Смысл колонки прежний: сколько байт файла отражено в индексе.
   `size < offset` — файл обрезали, `inode` другой — файл ротировали; и то и
   другое означает «выкинуть данные этого источника и перечитать».
3. Ничего не перепарсивается, если файл не менялся. Именно это и есть
   инкрементальность: холодный проход читает всё, дальше — только то, у чего
   сдвинулись `size`/`mtime`/`inode`.

## Контракт

```ts

export function defaultClaudeHome(): string // ~/.claude

Каталог базы — по правилам ОС, а не `~/.agentmeter`:
macOS `~/Library/Application Support/agentmeter/index.sqlite`,
Windows `%LOCALAPPDATA%\agentmeter\index.sqlite`,
Linux `$XDG_DATA_HOME/agentmeter/index.sqlite` (по умолчанию `~/.local/share`).
Переменная `AGENTMETER_INDEX` перебивает всё — на неё опираются тесты и проба.

// discover.ts
export interface SourceFile {

  parentPath?: string

```

```ts
// store.ts — единственное место, где что-то пишется в таблицы
export function putSource(
  db: Db,
  file: SourceFile,
  stat: { inode: number; size: number; mtime: number },
): void
export function putSession(db: Db, result: ParseResult, file: SourceFile): void
export function forgetSource(db: Db, path: string): void
```

`putSession` атомарен: в одной транзакции сносит `requests`/`tool_calls` этой
сессии и пишет заново, апсертит строку `sessions`, складывает диагностики.
Повторный вызов с тем же разбором обязан оставить базу в том же состоянии — это
и есть «повторный запуск не плодит дублей».

```ts

  failed: number // уронили парсер, записаны в diagnostics

  requests: number
  ms: number
}

export function ingestAll(db: Db, opts?: DiscoverOpts): IngestStats
export function ingestFile(db: Db, file: SourceFile): { parsed: boolean; requests: number }
```

## Схема: версия 2

Структура из 0.3 подходит целиком, добавляется одна вещь — тревога на
столкновение идентификаторов:

```sql
CREATE UNIQUE INDEX IF NOT EXISTS sessions_source ON sessions (source_path);
```

`SCHEMA_VERSION = 2`, миграция `{ version: 2, sql: '...' }` — совместимая, без
`rebuild`. Индекс здесь не для скорости: он превращает молчаливую перезапись
одной сессии другой в громкую ошибку. Почему это не теория — п. 2 подводных
камней.

Таблица `limit_windows` в этом этапе **не заполняется**. Окна лимитов — это 1.8,
и `LimitWindow` пока не несёт метки времени, а `observed_at` в схеме обязателен.
Дописывать поле в `types.ts` ради заглушки — трогать контракт M0, чего этот этап
не делает.

## Перечисление файлов — по правилу из 1.4, не по `**/*.jsonl`

**Claude**, корень `~/.claude/projects/`:

- сессия — `<uuid>.jsonl` **непосредственно** в папке проекта (папка проекта
  узнаётся по имени, начинающемуся с `-`);
- сабагент — `agent-*.jsonl` на **любой** глубине под каталогом `subagents/`.
  У воркфлоу они лежат на уровень глубже: `subagents/workflows/wf_<id>/`, и таких
  файлов больше, чем обычных (220 против 150).

Всё остальное под `projects/` транскриптом не является. Отдельно про
`journal.jsonl`: он лежит рядом с сабагентами воркфлоу, у него свой словарь
записей и ни одной цифры расхода. Разобрать его как сессию — значит завести в
индексе фантомную сессию без запросов, которая потом всплывёт в «Сегодня»
пустой строкой. Отсеивать при перечислении, а не объявлять дрейфом формата.
Готовая реализация правила — `isTranscript` в `scripts/probe/drift-scan.ts`.

Родитель сабагента выводится из пути: файл лежит под
`<проект>/<sessionId>/subagents/…` либо `<проект>/<stem>.subagents/…`, значит
родительский транскрипт — `<проект>/<sessionId>.jsonl` (соответственно
`<stem>.jsonl`). Рядом с каждым `agent-<id>.jsonl` лежит `agent-<id>.meta.json`
с `agentType` и `toolUseId` — оттуда берутся `sessions.agent_type` и
`parent_tool_use_id`.

`parseSubagents` в `claude/parse.ts` перевести на ту же функцию перечисления,
чтобы правило существовало в одном экземпляре, а не в двух расходящихся.

**Codex**, корень `~/.codex/sessions/`: `YYYY/MM/DD/rollout-*.jsonl`. Новая папка
дня появляется в полночь — вотчер обязан её увидеть (см. ниже про
`rediscoverMs`).

Дополнительные корни из `config.sources.extra` перечисляются по обоим правилам:
провайдер определяется по тому, какое из них сработало.

## Вотчер

- `fs.watch(root, { recursive: true })` на каждый корень. Работает на всех трёх
  платформах начиная с Node 20, но на Linux бывает недоступен на сетевых ФС —
  если конструктор бросил, откатываться на опрос `stat` по перечисленным файлам
  раз в 2 с. Молча оставлять пользователя без обновлений нельзя.
- События схлопывать по пути с задержкой `debounceMs` (300 мс): активный агент
  дописывает транскрипт по несколько строк в секунду, и разбирать файл на каждую
  строку незачем.
- Раз в `rediscoverMs` (30 с) — повторное перечисление: новые проекты, новая
  папка дня у Codex, удалённые файлы.
- Исчезнувший файл вычищается из базы через `forgetSource`.
- Вотчер не имеет права уронить процесс. `ENOENT`, `EPERM`, `EMFILE` при
  открытии, исключение парсера на битом файле — всё это ловится, пишется в
  `diagnostics` и не мешает остальным файлам.
- `config.index.watch = false` — вотчер не поднимается вовсе.

## Критерий готовности

```bash
npm run check
npm run fixtures:check
node --experimental-strip-types scripts/probe/index-live.ts
```

Плюс три прогона, которые обязаны остаться ровно такими же, как были, — это
защита от того, что правки в парсерах поехали:

```bash
node --experimental-strip-types scripts/probe/verify-live.ts   # 5 из 16 точных, худшее 3.30%
node --experimental-strip-types scripts/probe/drift-scan.ts    # 591 транскрипт, 0 незнакомых типов, 0 падений
node --experimental-strip-types scripts/probe/codex-live.ts    # 311 из 311 сходятся до токена
```

Если `verify-live` стал хуже — сломана модель, а не тест. Возвращаться и искать,
а не подкручивать порог.

`scripts/probe/index-live.ts` строит индекс во временной базе по живым логам и
проверяет семь вещей, каждую печатая отдельной строкой с числом:

1. **Холодный проход** по всему, что есть на диске, — **< 60 с**, с выводом
   времени, числа файлов, сессий и запросов.
2. **Индекс равен парсеру.** Для каждого источника суммы `input`, `output`,
   `cacheWrite`, `cacheRead` из таблицы `requests` совпадают с суммами по
   `parseSessionFile`/`parseRolloutFile` того же файла — **до токена**. Не
   выборочно, а по всем файлам.
3. **Повторный `ingestAll` ничего не перепарсивает**: `parsed = 0`,
   `skipped = scanned`, и число строк в `sessions`, `requests`, `tool_calls` не
   изменилось ни на единицу.
4. **Дочит.** Живой файл копируется во временную папку обрезанным на 80%,
   индексируется, потом дописывается хвост и `ingestFile` вызывается снова:
   замерить время — **< 100 мс**, и итоговые суммы обязаны совпасть с разбором
   целого файла.
5. **Обрезка.** Тот же файл укоротить до 50% — индекс обязан заметить
   `size < offset`, выкинуть данные источника и перечитать; сумма совпадает с
   разбором обрезанного файла, хвостов от прошлой версии не остаётся.
6. **Ротация.** Файл заменить другим по тому же пути (`rename` даёт новый
   inode) — то же самое: данные старой сессии в базе не остаются.
7. **Патологический роллаут** (единственная строка в 16 МБ, см. подводные
   камни) разбирается **< 300 мс**.

Модульные тесты в `packages/core/test/index/` — на фикстурах, с базой во
временном каталоге: перечисление (включая отсев `journal.jsonl` и подъём
сабагентов воркфлоу), идемпотентность `putSession`, миграция 1 → 2, поведение
вотчера на дописанном файле.

## Подводные камни

1. **`readJsonlLines` квадратичен по длине строки.** Он лежит скопированным в
   обоих парсерах и читает файл кусками по 64 КБ, делая на каждом
   `Buffer.concat([carry, chunk])` и заново просматривая весь накопленный буфер
   в поисках `\n`. Пока строки короткие, этого не видно. На роллауте
   `2026/04/16/rollout-…-019d95dc-….jsonl` одна строка занимает 15.97 МБ из 16 —
   и разбор занимает **3.7 секунды вместо 60 миллисекунд**: около 244 итераций,
   каждая копирует и просматривает в среднем 8 МБ. Вынести читатель в
   `packages/core/src/sources/jsonl.ts` в одном экземпляре и починить: копить
   куски массивом и склеивать один раз на найденной строке, искать `\n` только
   в новом куске, а не во всём буфере. Критерий — п. 7 пробы.

2. **Транскрипт сабагента содержит `sessionId` родителя.** Это не редкость и не
   край: на диске 591 файл даёт всего **330 уникальных идентификаторов**, у
   одной сессии 17 сабагентов и у всех восемнадцати файлов id один и тот же.
   `parseSubagents` проставляет `parentSessionId` и `isSidechain`, но `id` не
   трогает. В индексе, где `sessions.id` — первичный ключ, а
   `requests` ключуются `(session_id, seq)`, это означает, что сабагенты
   перезапишут друг друга и родителя, и в базе от восемнадцати сессий останется
   одна. Цифры при этом не сломаются с грохотом — они просто станут меньше.

   Чинить в парсере, а не в индексе: для сабагента `session.id` — это
   идентификатор из имени файла (`agent-a089514ce22c80943.jsonl` →
   `a089514ce22c80943`), а `parentSessionId` — прежний id из записей.
   Уникальный индекс по `sessions(source_path)` из версии 2 схемы стоит там же
   сторожем: если правило где-то нарушится снова, ingest упадёт с внятной
   ошибкой вместо тихой недостачи. Проверка: после холодного прохода число
   строк в `sessions` равно числу разобранных файлов.

   `scripts/probe/verify-live.ts` от этой правки не зависит — он суммирует
   результаты разбора, а не группирует по id, — но прогнать всё равно.

3. **`parseSubagents` разбирает родителя ещё раз** ради его `id`. При
   поштучном индексировании это лишний проход по самому большому файлу на
   каждого из семнадцати сабагентов. Родитель известен из пути (`parentPath` в
   `SourceFile`), парсить его второй раз не нужно.

4. **Сессия без запросов — это нормально.** Таких на диске 31 из 591: файл
   есть, разбор пустой. Их надо записать в `sessions` и не записать ни строки в
   `requests`, а не молча пропустить: в `doctor` они должны быть видны.

5. **Порядок записи.** Родителя индексировать раньше его сабагентов, иначе
   `parent_session_id` какое-то время указывает в никуда. Внешнего ключа на
   него нет, но проба это заметит.

6. **`STRICT`-таблицы не прощают типов.** `undefined` в биндинге `node:sqlite`
   — это ошибка, а не `NULL`; булево надо приводить к `0`/`1` руками. Пустая
   строка и `NULL` в `branch` — разные вещи, и в интерфейсе они будут выглядеть
   по-разному.

7. **Транзакция на весь холодный проход не годится** — 22 тысячи запросов и
   сотни тысяч строк в `tool_calls` в одной транзакции держат WAL в памяти.
   Транзакция на файл: она же единица атомарности и единица отката при падении
   разбора на середине.

8. **`mtime` в секундах на части файловых систем.** Опираться на связку
   `size` + `mtime` + `inode`, а не на один `mtime`: файл, дописанный в ту же
   секунду, обязан быть замечен по размеру.

9. **Ретеншн (`config.index.retentionDays`) в этот этап не входит.** Вопрос
   «что удалять из индекса и когда» в роадмапе открыт, и решать его заодно с
   вотчером не надо.
