# 1.10 — CLI: today, tasks, breakdown, limits, doctor

**Кто:** Codex · **Объём:** L · **Блокирует:** весь M2 (интерфейс рисуется поверх
этих же агрегатов)

Первый этап, где цифры показываются человеку. До сих пор всё, что посчитано
в 1.1–1.8, живёт в тестах и пробах: расход по вызовам, раскладка префикса, окна
лимитов — всё есть, и ничего нельзя посмотреть. CLI закрывает эту дыру и заодно
служит проверочным стендом для M2: экраны попапа и окна берут ровно эти
агрегаты, поэтому ошибка здесь всплывёт не в терминале, а в трее, через месяц.

Опасность этапа не в арифметике — она уже проверена. Она в том, что вывод —
первое место, где **неизвестное можно молча показать нулём**. Незаданный потолок
плана, неоткалиброванный вес `cache_read` (1.9), пустой индекс, сессия с
хвостовым прогревом — четыре разных «мы не знаем», и каждое обязано выглядеть
как «не знаем», а не как «ноль». Это не стилистика, это весь смысл продукта:
измеритель, который округляет незнание до нуля, хуже отсутствующего.

Второй по важности риск — двойной счёт сабагентов. Их транскрипты лежат в
индексе отдельными сессиями (так и надо: это настоящие вызовы API, и эталон
Claude Code их недосчитывает — см. `docs/roadmap/1.3-verify.md`). В итоге дня
они обязаны быть, в ленте задач — обязаны быть свёрнуты в родителя. Ошибка в
любую сторону даёт правдоподобное число: расход либо вырастет вдвое, либо
пропадёт, и оба варианта выглядят прилично.

Этап делится на две части, и их надо делать по порядку: без первой вторая
показывает пустую таблицу лимитов.

## Часть 1. Окна лимита попадают в индекс

Сейчас `limit_windows` в индексе пустая, и не потому что забыли писать: окно
живёт **поперёк файлов**. Лимит общий на аккаунт, одно пятичасовое окно
размазано по всем сессиям этих пяти часов, а ingest идёт файл за файлом и
видит только кусок. Собрать окно при разборе одного файла нельзя в принципе,
поэтому схема (уже переписана, версия 4) устроена так:

- `limit_observations` — сырые наблюдения Codex, привязанные к файлу. Это
  **вход** сборки. Пишутся при ingest, снимаются вместе с источником.
- `limit_windows` — **результат** сборки. Файлу не принадлежит, дописывать по
  частям нельзя, поэтому таблица целиком пересобирается после ingest.

### Контракт

Схема уже в
[`packages/core/src/index/schema.ts`](../../packages/core/src/index/schema.ts),
версия 4, миграция `{ rebuild: true }`. Читать её комментарии обязательно —
там записано, почему ключ окна это якорь, а не момент наблюдения, и почему
`used_percent` умеет быть `NULL`.

`ParseResult.limits?: LimitObservation[]` уже объявлен в
[`sources/types.ts`](../../packages/core/src/sources/types.ts). Заполняет его
только разбор Codex; у Claude лимитов в логах нет вовсе.

Появиться должно:

```ts
/** Наблюдения одного файла → индекс. Вызывается внутри транзакции putSession. */
export function putLimitObservations(
  db: Db,
  sourcePath: string,
  provider: Provider,
  observations: readonly LimitObservation[],
): void

/**
 * Полная пересборка `limit_windows` из наблюдений и запросов индекса.
 * Ничего не дописывает: таблица очищается и заполняется заново.
 */
export function rebuildLimitWindows(db: Db, limits: ClaudeLimits): LimitWindowStats

export interface LimitWindowStats {
  observations: number
  codex: number
  claude: number
}

/** Окна из индекса, по возрастанию якоря. */
export function readLimitWindows(
  db: Db,
  opts?: {
    provider?: Provider
    kind?: LimitWindowKind
    from?: number
    to?: number
  },
): LimitWindow[]
```

Сборку писать не надо, она готова:
`buildCodexWindows(observations)` и `buildClaudeWindows(requests, limits)` из
[`limits/`](../../packages/core/src/limits/). Второй принимает узкий
`LimitRequest` (момент и четыре счётчика) — специально, чтобы не собирать из
строк базы фальшивый `Request` с пустым списком тулов.

Три правила, которые нельзя вывести из сигнатур:

1. **Claude-окна строятся по всем запросам провайдера сразу**, из всех сессий,
   включая сайдчейновые, `synthetic` и восстановленные (`origin` не `log`).
   Фильтров нет и быть не должно: провайдер эти вызовы посчитал, значит и лимит
   их съел. Отфильтровать — единственный способ занизить расход так, что всё
   будет выглядеть аккуратно.
2. **Расход Codex-окон не считается.** Провайдер отдаёт точный процент, и наш
   счёт рядом с ним был бы вторым мнением ни о чём. Все шесть колонок
   `usage_*` у Codex остаются `NULL` — это «не считали», а не «ноль».
3. **`rebuildLimitWindows` вызывается после `ingestAll` и после пачки событий
   вотчера**, одной транзакцией с очисткой. `ClaudeLimits` берётся из конфига
   (0.5); у `ingestAll` для этого появляется необязательный параметр, по
   умолчанию — `DEFAULT_CONFIG.limits.claude` (там всё `null`, и это честно:
   без конфига проценты Claude неизвестны).

Дублировать разбор `rate_limits` нельзя. Сейчас его умеет только
`readLimits(path)`, который читает файл отдельно; после этапа разбор
`rate_limits` должен жить в одном месте, а `readLimits` и `parseRolloutFile`
быть двумя его вызывающими. Второе чтение файла ради наблюдений — не вариант:
между двумя чтениями файл успевает измениться, и это не теория (см. 1.5).

### Критерий готовности

```bash
npm run check
npm test -w packages/core -- limits
node --experimental-strip-types scripts/probe/limits-live.ts
```

Плюс новый тест `test/index/limit-windows.test.ts`, и вот что он обязан делать:
**прогнать эталон 1.8 через базу**. Для каждого файла из `fixtures/limits/` по
отдельности, в свежий индекс: ingest → `rebuildLimitWindows` →
`readLimitWindows` → результат совпадает с `*.expected.json` **до поля**, ровно
как в существующем `test/limits.test.ts`, только путь другой. Это единственная
проверка, которая ловит потерю наблюдений при записи в базу; сравнение
`buildCodexWindows` с самим собой её не заменяет.

По отдельности — потому что окна Claude строятся по всему индексу сразу, и
чужие фикстуры в базе их изменят. Отдельным тестом: три файла Codex,
загруженные вместе, дают объединение своих окон без изменений (цепочки
`weekly` из `codex-limits` и `codex-limits-new` не пересекаются — проверить, а
не поверить на слово; если пересеклись, сообщить, а не править эталон).

Ещё два теста: пересборка идемпотентна (два вызова подряд дают одинаковую
таблицу) и исчезнувший файл уносит свои наблюдения, а следующая пересборка —
свои окна.

### Контракт

```ts
export interface DayRange {
  from: number
  to: number
}
/** Границы дня с учётом ui.dayStartsAtHour в локальной зоне. */
export function dayRange(at: number, dayStartsAtHour: number, offsetDays?: number): DayRange

export interface Totals {
  input: number
  output: number
  cacheWrite: number
  cacheRead: number
  total: number
  requests: number
}

export function todayReport(db: Db, range: DayRange): TodayReport
export function taskRows(db: Db, range: DayRange): TaskRow[]
export function breakdownReport(
  db: Db,
  scope: { range: DayRange } | { sessionId: string },
): BreakdownReport
export function limitsReport(db: Db, at: number, limits: ClaudeLimits): LimitsReport
export function doctorReport(db: Db, config: Config): DoctorReport
```

Поля отчётов подбираются под то, что печатают команды, — здесь свобода. Не
свобода — семь правил ниже.

**1. Сабагенты считаются один раз.** В `todayReport` — вместе со всеми, это
настоящие вызовы API. В `taskRows` — свёрнуты в родителя (расход, тул-коллы и
счётчик сабагентов уходят в его строку). Если родителя в наборе нет, сабагент
показывается своей строкой: пусть выглядит странно, но расход не исчезает.
Отсюда обязательное тождество: `Σ taskRows.totals == todayReport.totals` на
одном и том же диапазоне.

**2. Неизвестное печатается как неизвестное.** `usedPercent === null` — это
`—` и причина рядом («потолок плана не задан», «вес cache_read не откалиброван,
этап 1.9»), никогда не `0%`. В `--json` — `null`, никогда `0`.

**3. Оценка помечается.** `exact === false` у окна и сессии с восстановленными
запросами (`origin != 'log'`) печатаются со знаком `≈`. В `--json` — булев
флаг рядом со значением.

**4. Пустой индекс — не ноль.** Если в базе нет источников, команда пишет
«индекс пуст, запустите `agentmeter index`» и не рисует таблицу нулей. То же
для пустого дня: «за 9 августа записей нет».

**5. Развёртка по тулам показывает долю оценки.** У `tool_calls` есть
`marginal_basis`: `measured` — дельта измерена, `split` — поделена между
параллельными вызовами, `unknown` — не восстановима. `breakdown` показывает эти
три числа раздельно, а не одну сумму. У Codex через дележ идёт 72% расхода
(он вызывает тулы пачками), и выдавать это за измеренное нельзя.

**6. Границы дня — локальные, метки времени — UTC.** `ui.dayStartsAtHour` из
конфига, день это `[начало, +24 ч)`. Пятичасовое окно лимита ходит через
полночь и к календарным суткам отношения не имеет — не пытаться их
согласовать, это разные вещи (разведка 1.8).

**7. Перед чтением команда доводит индекс.** `ingestAll` на тёплом проходе
стоит 15 мс, на холодном 2.8 с — дешевле, чем показать вчерашние числа. Флаг
`--no-ingest` отключает.

### Команды

```
agentmeter today     [--day YYYY-MM-DD] [--days N] [--provider claude|codex] [--json]
agentmeter tasks     [--day YYYY-MM-DD] [--limit N] [--json]
agentmeter breakdown [--day YYYY-MM-DD] [--session <id>] [--by tool|server|skill|agent|model] [--json]
agentmeter limits    [--json]
agentmeter doctor    [--json]
```

Общие флаги: `--index <path>`, `--config <path>`, `--no-ingest`, `--json`.
Коды возврата: `0` — всё хорошо, `1` — `doctor` нашёл ошибки разбора
(`kind = 'parser_error'`; незнакомые типы записей ошибкой не считаются, это
норма по 1.4), `2` — неверные аргументы.

Что печатает каждая:

- **today** — итог дня, разбивка по провайдерам, моделям, проектам и часам,
  число задач. Знак `≈`, если в дне есть сессии с восстановленными запросами.
- **tasks** — лента задач дня: время, длительность, проект, ветка, модель,
  заголовок, токены, тул-коллы, число свёрнутых сабагентов.
- **breakdown** — развёртка расхода по выбранной оси; для `tool` — три колонки
  по `marginal_basis`; для `server` — суммы по MCP-серверам; для `skill` — из
  `requests.skill`; для `agent` — по `sessions.agent_type`.
- **limits** — окна каждого вида по обоим провайдерам: процент, до сброса,
  точное/оценка, причина отсутствия процента. Закрытое окно — не текущее.
- **doctor** — путь и версия схемы, счётчики источников и запросов, незнакомые
  типы записей с версиями CLI, битые строки, ошибки разбора, состояние
  калибровки (`cacheReadWeight`, потолки) и число сессий с измеренной поправкой.
  Это отчёт 1.4 плюс то, что мешает верить цифрам.

Оформление — на усмотрение исполнителя: цвета не обязательны, ширина 80,
человекочитаемые числа сокращать (`1.2M`), в `--json` — целые.

4. Окна одного вида и провайдера не пересекаются.
5. Число окон Codex из индекса равно числу окон, посчитанных напрямую из

## Подводные камни

**Сабагент носит `sessionId` родителя.** Внутри файла
`agent-<id>.jsonl` лежит идентификатор родительской сессии, а не свой: 591 файл
на диске давал 330 уникальных. Личность сабагента берётся из имени файла, и
индекс это уже делает правильно (в фикстурах сессия `a6bf337b0067775dd` при
родителе `92cc27dc…`). Если в запросе к базе где-то появится группировка по
`sessions.id` с доверием к содержимому файла — сабагенты схлопнутся с
родителем, и расход просто станет меньше, без единого исключения в логах.

**Восстановленные запросы — не мусор.** `origin = 'reconstructed'` означает
запрос к API, которого нет в транскрипте, но который провайдер посчитал
(восстановлен по разрыву цепочки кэша, 1.3). В фикстурах их 8 из 134. Их надо
складывать наравне и помечать сессию знаком `≈`, а не прятать.

**Строка `assistant` — не запрос.** Один ответ API пишется несколькими
строками с одним `requestId`; парсер это уже схлопнул, но если в `query/`
появится счёт «запросов» по строкам транскрипта, число вырастет в разы.
В индексе единица запроса — пара `(session_id, seq)`.

**Процент окна — максимум наблюдений, а не последнее.** Снимок лимита приезжает
из ответа API и при параллельных запросах отстаёт: худший случай на живых логах
57% → 1% → 57% за 13 секунд. `buildCodexWindows` это уже делает; важно не
«улучшить» его при переносе в базу, взяв последнее наблюдение как более свежее.

**Вид окна — по длине, а не по имени слота.** До Codex CLI 0.145.0 `primary`
был пятичасовым, с 0.145.0 стал недельным, а `secondary` исчез. Имени слота нет
ни в модели, ни в схеме — не возвращать его.

**`node:sqlite` помечен экспериментальным**, доступ к нему только через
интерфейс `Db`. Никаких `db.db.prepare` из `query/`.

**Локаль.** Интерфейс русский (`ui.locale`), даты и числа форматировать через
`Intl` с локалью из конфига, а не строками вида `toLocaleString('ru-RU')`
вразнобой.
