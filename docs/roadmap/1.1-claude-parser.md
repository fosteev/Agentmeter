# 1.1 — Парсер Claude Code

**Кто:** Codex · **Объём:** L · **Блокирует:** 1.3, 1.5, 1.6 · **Ждёт:** 0.2, 0.6 — оба готовы

Превращает `~/.claude/projects/<slug>/<sessionId>.jsonl` в нормализованную
модель. Дальше на этих объектах стоит вообще всё, поэтому парсер обязан быть
скучным и буквальным: никаких догадок, никакого «похоже, тут имелось в виду».

## Файлы

```
создать:    packages/core/src/sources/claude/parse.ts
            packages/core/src/sources/claude/live.ts
            packages/core/src/sources/claude/index.ts

не трогать: packages/core/src/sources/types.ts   ← контракт, задан
            packages/core/src/sources/codex/**   ← чужой этап
            fixtures/**                          ← только читать

```

## Контракт

Типы `Session`, `Request`, `ToolCall`, `ParseResult`, `ParseDiagnostics` заданы
в `packages/core/src/sources/types.ts`. Менять их нельзя. Если чего-то не
хватает — остановиться и сказать, а не дописывать поля.

```ts
parseSessionFile(path: string): ParseResult
parseSessionChunk(path: string, fromOffset: number): { requests: Request[]; offset: number }
parseSubagents(sessionPath: string): ParseResult[]
listLiveSessions(dir?: string): LiveSession[]
```

`parseSessionChunk` нужен индексу (1.5) для дочитывания и обязан корректно
обрабатывать обрыв на середине строки: вернуть оффсет начала неполной строки,
а не проглотить её.

## Три правила, без которых цифры врут

Всё это выяснено разведкой на живых логах и проверено против эталона самого
Claude Code. Не переоткрывать, не «упрощать».

**1. Один вызов API — несколько строк, и строки не одинаковы.** Строки одного
`requestId` идут по одной на блок контента, а `output_tokens` в ранних из них
частичный: стриминг наращивает его по ходу ответа. Суммировать построчно —
завысить в разы, брать первую строку — недобрать вывод втрое и больше.
Схлопывать **максимумом по каждому полю** `usage`.

**2. Часть запросов в лог не пишется, но восстанавливается точно.** Префикс
запроса `N+1` обязан равняться префиксу `N` плюс записанное на `N`:

```
cacheRead(N+1) == cacheRead(N) + cacheWrite(N)
```

Больше — значит между ними прошёл незаписанный служебный запрос. Его
стоимость известна целиком: прочитано `cacheRead(N) + cacheWrite(N)`, записано
ровно на величину разрыва. Такой запрос попадает в результат как обычный
`Request` с `origin: 'reconstructed'`, `synthetic: true`, `requestId` вида
`reconstructed:<requestId предыдущего>` и `ts` предыдущего запроса.

Хвостовой такой запрос — после последнего ответа сессии — следа не оставляет и
**не восстанавливается**. Это известная недостача, её закрывает 1.3, здесь
ничего изобретать не нужно.

**3. Сабагенты пишут свои транскрипты** в
`<каталог проекта>/<sessionId>/subagents/agent-<agentId>.jsonl`, рядом
`agent-<agentId>.meta.json` с `agentType`, `description`, `toolUseId`,
`spawnDepth`. Это обычные транскрипты с `isSidechain: true`. `parseSubagents`
возвращает их как отдельные `ParseResult` с заполненными `parentSessionId`,
`parentToolUseId` и `agentType`. Складывать их в родителя — не здесь.

## Что откуда берётся

| поле | источник |
|---|---|
| `Request.input/output/cacheWrite/cacheRead` | `assistant.message.usage.*`, схлопнуто максимумом |
| `Request.cacheWrite5m/1h` | `usage.cache_creation.ephemeral_{5m,1h}_input_tokens` |
| `Request.model`, `requestId`, `ts` | `assistant.message.model`, `requestId`, `timestamp` (ISO → epoch ms) |
| `Request.skill` | `assistant.attributionSkill` |
| `Request.isSidechain` | `assistant.isSidechain` |
| `Request.contextTokens` | `input + cacheRead + cacheWrite` этого запроса |
| `Request.compacted` | префикс обвалился против предыдущего запроса — контекст сжали |
| `Request.origin`, `synthetic` | см. правило 2 |
| `ToolCall.id`, `name` | `assistant.message.content[].tool_use` |
| `ToolCall.kind`, `server` | `mcp__<server>__<tool>` → `mcp`; `Agent`/`Task` → `agent`; `Skill` → `skill`; `WebSearch`/`WebFetch` → `web`; иначе `builtin` |
| `ToolCall.resultBytes` | длина сериализованного `user.toolUseResult`, найденного по `tool_use_id` |
| `ToolCall.hasImage` | в `tool_result.content` есть блок `type: image` |
| `Session.title` | `ai-title.aiTitle`, последняя в файле |
| `Session.firstPrompt` | `last-prompt.lastPrompt`, первая |
| `Session.cwd`, `branch`, `model`, `cliVersion` | `assistant.cwd`, `gitBranch`, первый `model`, `version` |
| `Session.project` | последний сегмент `cwd`, а не slug каталога логов |
| `Session.entrypoint` | `~/.claude/sessions/<pid>.json`, поле `entrypoint`; нет файла → `unknown` |

`ToolCall.marginalTokens` **здесь не считается** — это этап 1.6. Оставить 0.

## Критерий готовности

```bash
npm test -w packages/core -- claude
```

Все фикстуры из `fixtures/claude/` разбираются без исключений, и для каждой
результат совпадает с `<сценарий>.expected.json` **глубоким сравнением**:
список запросов, суммы, порядок, тул-коллы с `resultBytes` и `hasImage`,
восстановленные запросы на своих местах.

`fixtures/claude/sidechain.subagents/` проверяет `parseSubagents` тем же
способом — там свои `.expected.json`.

## Данные

`fixtures/claude/` — восемь сценариев, к каждому `.expected.json`, плюс
`sidechain.subagents/`. Что каждая проверяет — таблица в
[`0.6-fixtures.md`](0.6-fixtures.md).

Формат `expected.json` — это спецификация в данных. Если разбор с ним не
сходится, ошибка в парсере, а не в фикстуре: `expected` построен отдельной
реализацией в `scripts/make-fixtures.ts` и проверен вручную.

## Подводные камни

1. **`usage.iterations`** существует и содержит разбивку по итерациям
   инференса. Не суммировать поверх верхнего уровня — будет двойной счёт.
   Гипотеза, что там прячется недостача, проверена и отпала.

2. **Не все записи — то, чем кажутся.** В файлах встречаются типы `mode`,
   `permission-mode`, `attachment`, `file-history-delta`, `file-history-snapshot`,
   `queue-operation`, `system`, `ai-title`, `last-prompt`, `summary`.
   Незнакомый тип — пропустить и записать в `diagnostics.unknownRecordTypes`,
   а не падать.

3. **Файл читается построчно и лениво.** Самый большой на машине — 5.2 МБ,
   всего 321 МБ по 590 файлам. `JSON.parse` на строку, битую строку пропустить
   и посчитать в `diagnostics.malformedLines`.

4. **`toolUseResult` может быть огромным**, и его размер не равен тому, что
   ушло в промпт: на реальном `Read` в логе лежало 382 КБ, а в промпт попало
   2873 токена. Читать длину, не содержимое; в память результат не тащить.

5. **Живые сессии — отдельный источник.** `~/.claude/sessions/<pid>.json`
   переживает смерть процесса, поэтому pid обязательно проверять на живость,
   иначе в трее навсегда повиснут мёртвые агенты.

6. **`timestamp` в UTC**, а «сегодня» у пользователя локальное. Парсер отдаёт
   epoch ms и в часовые пояса не лезет.
