# 1.9 — Настоящие лимиты Claude из statusline и калибровка `cache_read`

**Кто:** сам · **Объём:** M · **Блокирует:** ничего формально; снимает пометку
«оценка» с лимитов Claude на всех экранах и закрывает последний долг M1

У Claude в логах нет ни процента лимита, ни шапки окна, ни веса `cache_read` —
разница между «считать чтение кэша» и «не считать» два порядка (339M против
4.3M за сутки), поэтому лимиты Claude до сих пор помечены оценкой, а
`limits.claude.cacheReadWeight` лежит `null`
([`config/types.ts:140`](../../packages/core/src/config/types.ts#L140)). Оказалось,
Claude Code сам отдаёт эти числа — не в транскрипт, а на stdin команде
`statusLine`. Этап ставит хук, копит снимки и выводит из них вес и шапку окна.
Сделать плохо — значит подогнать коэффициент под несколько точек и выдать
подгонку за измерение; тогда продукт начнёт врать в единственном месте, где
он обязан быть точным.

## Контракт

**Вход — JSON на stdin команды `statusLine`.** Замерено на Claude Code 2.1.85,
11 августа 2026, значимая часть:

```json
{
  "session_id": "…", "transcript_path": "…", "version": "2.1.85",
  "rate_limits": {
    "five_hour": { "used_percentage": 13,   "resets_at": 1786441200 },
    "seven_day": { "used_percentage": 14.0, "resets_at": 1786856400 }
  },
  "context_window": { "context_window_size": 200000, "used_percentage": 15 }
}
```

`resets_at` — **секунды** unix, не миллисекунды. `used_percentage` дробный
(наблюдалось `14.000000000000002`). Ключа `rate_limits` в объекте **нет вовсе**,
пока в сессии не прошёл первый запрос к API, — поле читается как опциональное,
его отсутствие не ошибка.

**Хук ничего не решает.** Он пишет полученный JSON в
`configDir()/usage-latest.json` целиком и, если в конфиге сохранён прежний
`statusLine` пользователя, прогоняет stdin через него и отдаёт его stdout
дословно. Своей строки при этом не печатает. Если прежнего не было — печатает
`5h 13% · 7d 14%`: только цифры и латиница, `t()` в хуке нет и быть не может, он
исполняется вне приложения.

**Дозапись журнала — в main.** Вотчер на `usage-latest.json`, дедуп по паре
(процент, `resets_at`) каждого окна, строка в `configDir()/usage.jsonl`:

```json
{"ts":1786441203119,"sessionId":"…","cliVersion":"2.1.85","contextWindowSize":200000,
 "fiveHour":{"pct":13,"resetsAt":1786441200},"sevenDay":{"pct":14.0,"resetsAt":1786856400}}
```

Прецедент журнала — `configDir()/lifetimes.jsonl` из 1.3.

**Выход** — уже существующие поля конфига, новых заводить не нужно:
`limits.claude.cacheReadWeight` (валидация 0..1,
[`validate.ts:69`](../../packages/core/src/config/validate.ts#L69)),
`limits.claude.fiveHourCap`, `limits.claude.weeklyCap`.
Сигнатура `buildClaudeWindows` не меняется — она уже принимает
`cacheReadWeight: number | null` и при `null` отдаёт `weighted: null`.

## Модель

Для снимка с процентом `p` и границей `resets_at` берём окно
`[resets_at − 5ч, resets_at)`, суммируем по запросам Claude внутри него до `ts`
снимка четыре компонента: `I`, `W`, `O`, `R`. Тогда

```
p/100 · cap = I + W + O + w · R
```

Неизвестных две, `cap` и `w`, и уравнение по ним **линейно**:
`(p/100)·cap − R·w = I + W + O`. Две точки задают решение, больше — МНК.
Считать отдельно по пятичасовым и недельным окнам: `cap` у них разный, `w`
обязан совпасть — это и есть проверка модели, а не пересчёт.

У Codex тот же вес добывался подбором по минимуму разброса (1.8, вышло ≈ 0.2)
именно потому, что процента не было. Здесь он есть, поэтому подбор заменяется
решением, а полученное `w` сверяется с кодексовым только глазами: провайдер
другой, переносить нельзя.

## Критерий готовности

```bash
npm run check
node --experimental-strip-types scripts/probe/usage-live.ts
```

Проба печатает число точек, `w`, `cap` по обоим окнам и остаток. Зелёным
считается: точек ≥ 20 из ≥ 3 разных пятичасовых окон, `w` внутри (0, 1), `cap`
между окнами расходится < 5%, медианное отклонение предсказанного процента от
наблюдаемого ≤ 2 п.п. Меньше точек — проба честно печатает «данных мало», вес
остаётся `null`, лимиты остаются оценкой. Это нормальный исход первого прогона,
а не провал: журнал копится днями.

## Подводные камни

1. **Процент считается по аккаунту, а не по машине.** Работа с другого
   компьютера, из веба или из Claude Desktop поднимает процент, не оставляя
   следа в нашем индексе, — и `cap` завысится. Окна, где процент вырос, а
   запросов у нас в них нет или их прирост несопоставим, обязаны выбрасываться
   из выборки, а не усредняться. Ровно этим больна ветка «cross-device» у
   Claude-Code-Usage-Monitor.
2. **Наша сумма систематически занижена** — служебный Haiku (пункт 20 CLAUDE.md,
   1.30% на эталоне) и хвостовые прогревы (1.3, ≤ 3.3%) в логах не лежат вовсе.
   Значит `cap` выйдет завышенным на единицы процентов. Это записывается в
   документ как измеренная систематика; вводить подгоночный множитель, чтобы
   красиво сошлось, нельзя.
3. **`cachedUsageUtilization` из `~/.claude.json` не использовать.** Поле есть и
   читается без сети, но не обновляется ни стартом CLI, ни открытием самой
   панели: замер 11 августа — снимку 12 часов, панель в это время показывала
   9% / 14%, в файле лежали 1% / 11%. Проценты там вдобавок целые.
4. **`https://api.anthropic.com/api/oauth/usage` не использовать.** Путь рабочий
   (токен из `~/.claude/.credentials.json`, заголовок
   `anthropic-beta: oauth-2025-04-20`), им живут claude-monitor и CodexBar, но он
   недокументирован, требует притворяться `User-Agent: claude-code/<version>` и
   жёстко 429-ит (anthropics/claude-code #31021, #31637). Для нас это второй
   сетевой вызов чужими креденшелами — прямо против обещания из README.
5. **Хук вызывается часто и из нескольких окон сразу.** Поэтому он
   перезаписывает один файл, а не дописывает журнал: дозапись с дедупом делает
   main, где она одна. Перезапись — через временный файл и `rename`, иначе
   вотчер поймает половину JSON.
6. **`statusLine` — настройка пользователя, и она может быть занята.** Прежнее
   значение сохраняем в свой конфиг, чужую команду вызываем и её вывод отдаём
   дословно. Снятие хука обязано возвращать ровно то, что было. Ставить без
   явного согласия нельзя — это правка чужого конфига.
7. **`node` в хуке не предполагать.** Claude Code ставится нативно, ноды на
   машине может не быть; хук — sh и cmd, вся логика в приложении.
8. **В `-p` statusline не зовётся вовсе**, снимков из headless-сессий не будет.
   Ретроспективы этап тоже не даёт: до установки хука лимиты неизвестны и
   остаются оценкой.
9. **`context_window_size` приезжает в том же JSON** и относится к пункту 12
   CLAUDE.md, где знаменатель контекста у Claude выводится из наблюдений. В
   журнал его пишем сразу, применение к
   [`live/context.ts`](../../packages/core/src/live/context.ts) — отдельной
   строкой, не в этом этапе.

## Что сделано иначе, чем в разведке

Пять решений разошлись с планом выше. Записаны здесь, чтобы через полгода
разница между документом и кодом не выглядела недосмотром.

1. **`resetsAt` в журнал пишется в миллисекундах**, хотя на stdin приезжают
   секунды. Перевод делает `parseStatusLine`, он же единственное место, которое
   видит исходный формат. Причина: `resetsAt` в
   [`LimitWindow`](../../packages/core/src/sources/types.ts) — миллисекунды, и
   второе поле того же имени в соседнем файле, но в секундах, однажды сложилось
   бы с первым.

2. **Тело хука лежит строкой в
   [`main/statusline-hook.ts`](../../apps/desktop/src/main/statusline-hook.ts), а
   не файлом в `resources/`.** Хук исполняется вне приложения, значит, лежать
   он обязан рядом с настройками — путь туда переживёт и обновление, и
   переустановку. А ресурс внутри бандла пришлось бы искать по пути, который в
   разработке и в упакованном приложении разный: ровно на этом в 5.1 сломался
   preload, и окно поднялось без единого канала. Строка в модуле такого пути не
   имеет вовсе. Ставится файл в `configDir()`, читать и удалять его руками
   можно, устаревшее тело переписывается при старте.

3. **Комментарии внутри хука — по-английски.** Он живёт вне приложения, `t()`
   там нет, а его windows-двойник обязан быть чистым ASCII: кодовая страница
   консоли превратила бы кириллицу в мусор. Своя строка состояния печатается
   как `5h 13% / 7d 14%` — разделитель ASCII по той же причине.

4. **Порог «чужого расхода» — доля от накопленного процента (5%), а не пункты.**
   Разведка предлагала выбрасывать окно, где процент вырос без наших запросов.
   Так и сделано, но с двумя уточнениями, которые нашлись на эталоне. Первое:
   одна и та же чужая тысяча токенов двигает пятичасовое окно в двадцать раз
   сильнее недельного, поэтому порог в п.п. был бы либо слеп к недельному, либо
   истеричен к пятичасовому. Второе: нулевым порог быть не может — служебный
   Haiku и хвостовые прогревы в логах не лежат принципиально (1.30% и ≤ 3.3%),
   и порог ноль объявлял бы чужой машиной каждую заглавную строку сессии. 5% —
   сумма обеих измеренных систематик, пол — 1 п.п.

5. **Заражённое окно обрезается с точки заражения, а не выбрасывается целиком.**
   Чужой расход смещает все последующие проценты окна и ни одного предыдущего.
   Для пятичасового окна, где чужое пришло первым, это и есть «выбросить
   целиком»; а недельное окно одно на всю неделю, и выбрасывать его целиком
   значило бы терять единственную проверку модели — совпадение веса между
   окнами разной длины.

6. **Отсев окон-выбросов идёт до общего решения, а не после.** Каждое окно
   решается своей парой (потолок, вес) по своим точкам, и сравниваются медианы.
   Проверено обратным: одно окно с чужим расходом уводит **общее** решение за
   пределы доли (вес выходил −0.17), и отсев, стоящий после него, не
   запускается вовсе.

7. **Потолки записываются в конфиг, только если человек не выбирал план.** Вес
   уходит туда всегда, когда калибровка сошлась: в логах его нет, спросить не у
   кого. А выбор плана — это заявление о подписке, и перебивать его измерением
   значит драться с кнопкой, которую человек только что нажал.
