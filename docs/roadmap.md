# Roadmap

От пустой папки до подписанных инсталляторов. Каждый этап заканчивается
проверяемым результатом — не «написан парсер», а «команда отработала зелёным».

Колонка «кто»: **сам** — решение неочевидно и ошибка не ловится тестом;
**Codex** — объём с ясным критерием готовности (через скилл `delegate-to-codex`).
Объём: **S** — один заход, **M** — половина дня, **L** — день и больше.

Этот файл — индекс и единственное место, где живут статусы. Развёрнутые брифы
по этапам лежат в [`roadmap/`](roadmap/) и пишутся на веху вперёд.
Реализация дизайна разобрана отдельно:
[`roadmap/design-implementation.md`](roadmap/design-implementation.md).

## Архитектура

```
packages/core/            чистый TypeScript, ничего не знает про Electron
  sources/claude/         разбор ~/.claude/projects/*.jsonl + sessions/*.json
  sources/codex/          разбор ~/.codex/sessions/**/rollout-*.jsonl
  sources/types.ts        нормализованная модель — общая для обоих провайдеров
  index/                  SQLite, инкрементальный дочит по (файл, оффсет, inode)
  attribution/            маржинальная дельта, рекуррентная стоимость, категории
  limits/                 окна, точные у Codex, оценочные у Claude
  query/                  агрегаты под экраны: today, tasks, breakdown, live
apps/cli/                 agentmeter today|tasks|breakdown|limits|doctor|verify
apps/desktop/             Electron: main (трей, вотчер, IPC) + renderer (React)
design/                   макет из Claude Design — эталон для вёрстки
```

Ядро отдельным пакетом не ради красоты: CLI поверх него сверяет цифры в
терминале, не запуская GUI. Пока цифры не сошлись, рисовать нечего.

### Нормализованная модель (0.2)

```ts
type Provider = 'claude' | 'codex'

interface Session {
  id: string
  provider: Provider
  cwd: string
  project: string
  branch?: string
  model?: string
  entrypoint?: string // cli | vscode | jetbrains | exec
  title?: string
  firstPrompt?: string
  startedAt: number
  endedAt: number
  parentSessionId?: string // сайдчейн сабагента
}

interface Request {
  // один вызов API
  sessionId: string
  seq: number
  requestId: string
  ts: number
  model: string
  input: number
  output: number
  cacheWrite: number
  cacheRead: number
  reasoning?: number // Codex отдаёт явно
  contextTokens: number // занято окна на этом запросе
  skill?: string // attributionSkill
  isSidechain: boolean
  compacted: boolean // скачок префикса — компакт контекста
  synthetic: boolean // служебный вызов, не пользовательский ход
  tools: ToolCall[]
}

interface ToolCall {
  id: string
  name: string
  kind: 'builtin' | 'mcp' | 'skill' | 'agent' | 'web'
  server?: string // для mcp__server__tool
  resultBytes: number // размер в логе — врёт, но нужен для дележа
  marginalTokens: number // посчитано атрибуцией — это правда
  hasImage: boolean
}
```

**1.3 закрыт исходом «измеренная поправка»** (решение от 9 августа 2026).
Хвостовые прогревы после последнего ответа сессии следа в логах не оставляют, и
их число зависит от времени жизни процесса, которого в логе нет вовсе — поэтому
исходный критерий «40 из 41 до токена» недостижим в принципе, а не «пока».
Остаток ≤ 3.3% чтения кэша, всегда в меньшую сторону, всегда кратен последнему
префиксу; такие сессии показываются со знаком `≈`. Замер зависимости перенесён
в 2.1, где вотчер и так видит рождение и смерть сессии — **сделано, журнал
`configDir()/lifetimes.jsonl` копит наблюдения с 10 августа 2026**; корреляция
недобора с временем жизни считается, когда наблюдений наберётся достаточно.

**1.5 закрыт с изменённым решением.** Дочитывания байтового хвоста не будет:
парсер даёт 150 МБ/с, и перечитать изменившийся файл целиком стоит 80 мс на
худшем живом файле при бюджете в 100 мс. Зато исчезает состояние между чанками,
а с ним оба места, где ошибка была бы тихой, — дедуп `token_count` у Codex и
схлопывание `requestId` у Claude. `parseSessionChunk`/`parseRolloutChunk`
удалены. Тройка `(path, inode, offset)` из 0.3 работает как задумана, читаем
только с нуля. Замеры: холодный проход 912 файлов — 2.8 с, повторный — 15 мс,
индекс совпал с парсером на всех 912 файлах до токена. Подробности и две
находки, менявшие цифры, — [`roadmap/1.5-index.md`](roadmap/1.5-index.md).

**1.6 закрыт.** Формула оказалась одна на обоих провайдеров:
`ctx(N+1) − ctx(N) − output(N)`, где `ctx` — весь промпт запроса, а `N+1` —
следующий **записанный** запрос. Реконструированные (1.3) при этом не теряются:
их `cacheWrite` уже сидит в `cacheRead` следующего записанного. Модель и эталон
с ручным расчётом каждого из 23 вызовов писал сам (`fixtures/attribution/`),
реализацию с тестами и пробой отдал в Codex — бриф
[`roadmap/1.6-attribution.md`](roadmap/1.6-attribution.md).

Разведка дала две вещи, которых в задумке не было. Первая: у Codex
`token_count` пишется **между** вызовом и его результатом, поэтому каждый вызов
попадал в модель дважды — именованным с нулём байт и безымянным с байтами на
следующем запросе. Суммы токенов это не ломало, и `codex-live` молчал; список
тулов и веса при дележе — ломало полностью. Вторая: формулу удалось сверить с
источником, который писали не мы, — Codex кладёт в текст результата
`Original token count`, и медиана отношения к нашей дельте равна **1.00** на 519
вызовах.

Что показали живые логи после закрытия: измерено 69.5% вызовов Claude (67.0%
токенов) и 34.5% Codex (27.9%); через дележ, то есть через оценку, проходит
33.0% расхода у Claude и **72.1% у Codex** — он вызывает тулы пачками. Неизмеримо
1.9% и 1.3% вызовов, и они несут 0.0% токенов. Заодно выяснилось, что вызов
`Skill` попадает в неизмеримые: тело скилла приезжает отдельным пользовательским
текстом, и дельта перестаёт быть только результатом тула. На разбивку по скиллам
это не влияет — она идёт из `attributionSkill`, а не из арифметики.

**Что 1.7 не считает и это известно:** глобальный `~/.claude/CLAUDE.md` и файлы
памяти в раскладку не попадают — учитывается только `CLAUDE.md` из корня

удаляемый пользователем текст, записанный в неудаляемое, — то есть ровно та

домашний каталог нельзя, тесты станут машинозависимыми. Правильное место —
опция с путями из `config.sources`, отдельной мелкой правкой.

**Разведка 1.7 дала три вещи.** Первая — блоки стартового
префикса лежат в транскрипте дословно, записями `attachment`: листинги скиллов
и сабагентов, имена отложенных тулов, инструкции MCP, вложенные `CLAUDE.md`.
Парсер их сейчас выбрасывает. Вторая — отложенные тулы обвалили цену MCP в 17
раз: serena стоит 6007 токенов жадно и 349 отложенно, и рекомендация «отключи
неиспользуемый сервер» без различения режимов врёт на порядок. Третья — байт на
токен разный по категориям (2.60 на списке имён против 4.11 на прозе), и общая
константа промахивалась на 36% на первом ходе пользователя; поймала это парная
сверка на 685 парах живых сессий, она же и стала критерием этапа. Константы
меряются стендом `scripts/probe/calibrate-prefix.sh` — известный текст кладётся
в `CLAUDE.md` пустой папки, разница `ctx` даёт токены без токенизатора, прогон
стоит цент. Модель и эталон — [`roadmap/1.7-prefix.md`](roadmap/1.7-prefix.md),
[`fixtures/prefix/`](../fixtures/prefix/).

**1.8 закрыт.** Окна собирает `packages/core/src/limits/`, проба
`limits-live.ts` даёт шесть зелёных проверок на живых логах: 29 748 наблюдений
разложились по 168 окнам без нарушений, якорь предсказан с точностью 60 с на
126 из 135 пятичасовых окон, перекрытий нет, у файлов CLI ≥ 0.145.0 нет ни
одного окна `fiveHour`, а 18 326 запросов Claude покрыты окнами до токена.
Модель и эталон с ручным расчётом писал сам
([`roadmap/1.8-limits.md`](roadmap/1.8-limits.md),
[`fixtures/limits/`](../fixtures/limits/)), реализацию с тестами и пробой отдал
в Codex.

Две правки после ревью делегированного кода. Первая: наблюдение, чей якорь не
совпал ни с одним известным окном, приписывалось к последнему окну цепочки —
то есть чужой процент мог вырасти на снимке из другого окна. Теперь такое
наблюдение открывает своё окно на своём месте в цепочке. На живых данных случай
не встретился ни разу, но молчаливое завышение процента лимита — ровно тот класс
ошибки, ради которого этап и делался. Вторая: проверка 3 в пробе была
тавтологичной — сравнивала `max(prev, x)` с `prev` и потому не могла провалиться
никогда. Переписана в проваливаемую: процент окна обязан равняться максимуму по
наблюдениям (0 расхождений), и в данных обязаны быть сами протухшие снимки —
3 окна, где последнее наблюдение ниже максимума, при 109 сырых падениях.

Разведка дала три вещи, которых в задумке не было.

Первая: **`primary` сменил смысл.** До Codex CLI 0.145.0 `primary` — окно на
300 минут, `secondary` — недельное; с 0.145.0 `primary` стал недельным, а
`secondary` исчез. На диске 14 716 наблюдений старой раскладки и 252 новой.
Разбор по имени слота показывал бы недельный расход как пятичасовой — молча,
без единой ошибки разбора. Поэтому вид окна выводится из его длины, а
`LimitWindow.kind` в контракте 0.2 переписан с `primary | secondary` на
`fiveHour | weekly | monthly | other`.

Вторая: **наблюдения приезжают не по порядку.** `token_count` несёт снимок
лимита из того ответа API, который его породил, и при параллельных запросах
более старый снимок ложится в лог позже. 68 падений процента в пятичасовых
окнах и 41 в недельных, худшее — 57% → 1%, через 13 секунд снова 57%. Процент
окна — максимум наблюдений, а не последнее.

Третья: **окно фиксированное и якорится на первом запросе после истечения
прошлого.** Проверено против чужого числа: `|resets_at − длина − момент первого
наблюдения| ≤ 60 с` у 126 из 135 пятичасовых окон, медиана 10 с. Эта же модель
переносится на Claude, у которого лимитов на диске нет вовсе — проверено по
всему `~/.claude`, включая `sessions/*.json` и `stats-cache.json`.

Заодно измерено то, чего никто не обещал: **вес прочитанного из кэша в
подписочном лимите Codex**. Числитель от провайдера, знаменатель наш —
подбор на окнах одной модели даёт минимальный разброс при весе ≈ 0.2, а вес 0
проигрывает втрое (CV 5% против 17% на недельных окнах `gpt-5.5`). То есть
`cache_read` считается, но со скидкой примерно впятеро. В модель 1.8 это не
входит — у Codex процент и так точный, — но задаёт правдоподобный диапазон для
1.9, где тот же вопрос по Claude пока стоит с неопределённостью в два порядка.
Переносить 0.2 в конфиг Claude по аналогии нельзя: 1.9 существует ради ручной
сверки с `/usage`.

Тогда же исправлен критерий `verify-live`: он до сих пор требовал схождения
**всех** сессий до токена и потому возвращал единицу при принятом исходе 1.3.
Теперь порог тот, которым 1.3 закрыт: расхождение ≤ 3.5% и не меньше 5 точных
сессий.

**1.10 закрыт.** Окна лимита доехали до индекса, появился `packages/core/src/query/`
и пять команд CLI. Проба `cli-live.ts` даёт шесть проверок на живых логах: итог
`query/` совпадает с прямым прогоном парсера по 899 файлам (33 228 запросов, ноль
расхождений), `Σ tasks == Σ today` на каждом из 7 дней, каждый запрос Claude
покрыт ровно одним пятичасовым и одним недельным окном (21 542 запроса, ноль
нарушений), 237 окон без пересечений, окна Codex из индекса совпадают с прямым
`readLimits` пополем, и при неоткалиброванном весе `cache_read` ни одно окно
Claude не получает числового процента. Ручной эталон восьми фикстур Claude плюс
сабагент и роллаут Codex (60 064 / 55 349 / 338 669 / 5 296 487, 134 запроса)
пинится тестом `query/reports`, а снапшот вывода проверяет только вёрстку —
числа в нём замаскированы.

Правки после ревью делегированного кода. Первая: `watchSources` принимал
`DiscoverOpts` и потому терял `claudeLimits` по дороге в `ingestAll`, который
теперь пересобирает окна. Сегодня это невидимо (вес не откалиброван, проценты и
так `null`), но после 1.9 первое же изменение файла молча заменило бы
посчитанный процент на «неизвестно» — расход в трее просто исчез бы после
сохранения любого лога. Вторая: проверка 5 в пробе сравнивала только длины
списков окон, то есть не ловила ни чужой процент, ни уехавший якорь — ровно те
две ошибки, ради которых делался 1.8. Переписана на пополевое сравнение.
Заодно вылечено мигание теста вотчера (потолок ожидания 2 с при задержке
`fs.watch` на загруженной macOS) и множественное число в шапке `today`.

**Что известно и оставлено как есть:** `limitsReport` пересобирает окна на
каждом чтении — это скрытая запись из читающего модуля и полный проход по
запросам на каждый опрос трея; переезжает в 2.1, где живой слой и так решает,
когда пересчитывать. И `dayRange` держит сутки ровно 24 часа, поэтому дважды в
год на переводе часов соседние дни перекрываются или расходятся на час.
**Оба закрыты в 2.1**, см. ниже.

**Схема индекса поднята до версии 4** — разведка 1.10 нашла, что таблица
`limit_windows` осталась от контракта, написанного до 1.8, и в неё вдобавок
никто ничего не писал. Ключом был момент наблюдения вместо якоря окна, не было
ни `starts_at`, ни расхода, а `used_percent NOT NULL` запрещал единственное
честное значение для Claude — «неизвестно». Рядом появилась
`limit_observations`: окно живёт поперёк файлов, поэтому в индекс кладётся вход
сборки, а результат пересобирается целиком после ingest. Миграция —
`{ rebuild: true }`, и она же вскрыла второй огрех: ветка пересборки базы не
выполнялась ни разу с 0.3, а `PRAGMA foreign_keys = OFF` внутри транзакции —
no-op, из-за чего снос таблиц падал на «no such table». Бриф этапа —
[`roadmap/1.10-cli.md`](roadmap/1.10-cli.md).

Расследование продвинулось: недостающий класс найден — часть запросов к API в
транскрипт не пишется, но восстанавливается по разрыву цепочки кэша. Недобор
упал с 5–15% до ±3%, пять сессий из пятнадцати сходятся до токена. Осталась
хвостовая часть, следа не оставляющая. Заодно выяснилось, что сабагенты пишут
собственные транскрипты, а эталон Claude Code их недосчитывает. Подробности —
[`roadmap/1.3-verify.md`](roadmap/1.3-verify.md).

**2.1 закрыт.** Живой слой — `packages/core/src/live/`, шестая команда CLI
`agentmeter live [--json]`, проба `scripts/probe/live-probe.ts`: девять
проверок, каждая названа по поломке, которую ловит, и каждая показана красной
мутацией кода. Снимок стоит 4.7 мс медианы на живом индексе (26 670 запросов),
новая сессия видна за 1007 мс при пороге 2 с, исчезнувшая — за 1000 мс при
пороге 5 с.

Заодно закрыты оба долга 1.10. `limitsReport` больше не пересобирает окна:
пересборку делает тот, кто менял вход, — `ingestAll` после прохода (и только
если что-то действительно разобрано) и `ensureLimitWindows` по отпечатку
`ClaudeLimits` в `meta`. Без отпечатка проценты замёрзли бы на первом конфиге,
и устаревший ответ выглядел бы как честное «план не задан». `dayRange` теперь
считает день календарно, от начала до начала следующего: на переводе часов
сутки длятся 23 или 25 часов, но соседние дни стыкуются без нахлёста и без
дыры.

**Замер хвостовых прогревов (долг 1.3) пошёл копиться.** Журнал —
`configDir()/lifetimes.jsonl`, по записи на сессию: когда увидели впервые,
когда видели в последний раз, когда наблюдали смерть процесса и каким был
последний записанный запрос. Искомое — `endedAt − lastRequestTs`. Журнал лежит
**вне индекса** сознательно: индекс полностью производен от логов, и его
чинят сносом с перечитыванием (правило 3 в `schema.ts`, уже применялось в
версии 4) — единственным невосстановимым данным там не место. Смерть, которую
не наблюдали (выключили приложение, машина уснула), остаётся `null`: здесь
«не знаем» дороже правдоподобного числа.

Разведка дала четыре вещи, которых в задумке не было.

Первая: **`entrypoint` на диске не тот, что в контракте.** В файлах лежат
`claude-vscode`, `claude-desktop`, `cli`, а белый список знал `vscode` и
`desktop` — 8 живых сессий из 9 схлопывались в «неизвестно», и это выглядело
как свойство данных, а не как ошибка разбора.

Вторая: **`procStart` записан в UTC**, хотя выглядит локальным временем
(`Mon Aug 10 07:11:48 2026` у процесса, стартовавшего в 10:11:48 по местному).
`ps` печатает локальное. Наивная сверка времени старта промахнулась бы на
смещение зоны и объявила переиспользованным каждый живой pid — проверка,
поставленная ради борьбы с вечным агентом в трее, сама бы стёрла список.

Третья: **файл сессии пишется один раз при старте** — `mtime` совпал со
`startedAt` на всех девяти файлах. Значит, признак активности берётся только из
транскрипта; `mtime` файла сессии дал бы «все агенты думают всегда». Сокет
`/tmp/cc-socks/<pid>.sock` тоже не годится: он есть у 4 файлов из 9, только у
CLI 2.1.226.

Четвёртая: **у Codex реестра живых процессов нет вовсе** — проверено по всему
`~/.codex`, включая `process_manager/`, `ipc/` и `session_index.jsonl`. Живость
там выводится из свежести роллаута, поэтому в снимке рядом с агентом едет
`liveness: 'process' | 'silence'`: у Claude смерть — факт, у Codex догадка, и
путать их в интерфейсе нельзя.

Две правки по ходу. Первая: `ps` вызывался на каждый снимок, и это была вся его
цена — 15.6 мс медианы. Время старта процесса не меняется, пока процесс жив,
поэтому проверенные pid кэшируются между опросами; после этого снимок стоит
4.7 мс. Вторая: тест вотчера всё-таки мигал, и «лечение» из 1.10 не работало —
потолок ожидания подняли до 15 с внутри `waitFor`, а собственный потолок vitest
остался 5 с, то есть тест умирал раньше, чем успевал дождаться. Теперь потолок
задан у самого теста, а запасной переобход в нём — 1 с: проверяется контракт
«вотчер дочитает изменившийся файл», а не задержка `fs.watch`, которой на
сетевой файловой системе не бывает вовсе.

**2.2 закрыт.** Состояния считает `packages/core/src/live/state.ts`, и делится
это на два шага: из хвоста лога читается **чей ход** (факт источника), из хода и
тишины выводится состояние (наше суждение). Первый шаг разный у провайдеров,
второй общий. Проба `scripts/probe/states-live.ts` — восемь проверок, каждая
названа по поломке и каждая показана красной мутацией кода.

Главная из них единственная, которая сверяется не с собой: **предсказание
проверяется тем, что источник записал следующим.** Если ход у человека, дальше
в логе обязана лежать его реплика; если у агента — ответ модели либо результат
инструмента. Разбор хода смотрит только назад и о будущем не знает ничего.
3252 перехода на 251 файле, **ноль ошибок**.

Разведка дала четыре вещи, и три из них меняли ответ.

Первая: **тип последней записи не годится в признак.** После значимой записи в
лог ложатся учётные — `attachment`, `file-history-snapshot`, `last-prompt`,
`mode`, `queue-operation`, `ai-title`, `permission-mode`, — и последней в файле
оказывается именно учётная у **233 файлов из 251**. Поле `lastEventKind`,
заведённое в 2.1 как вход для 2.2, отвечает про них, а не про ход.

Вторая: **порядок записей в файле не хронологический.** Живой пример:
`stop_hook_summary` с меткой 08:00:11 лежит после `queue-operation` с меткой
08:08:04. Сортировать по меткам нельзя — «последняя» значит последняя по
положению.

Третья: **`stop_sequence` у модели не встречается вовсе.** Все 17 таких записей
на диске помечены `model: "<synthetic>"` — их сочинил сам CLI («Credit balance
is too low», «No response requested.»), и других синтетических записей нет ни
одной. То есть «модель закончила необычно» на диске означает «модель не
отвечала».

Четвёртая: **отличить «спросил» от «долго работает» по времени нельзя.** У
`AskUserQuestion` медиана ожидания 50 с и максимум 15 часов при p95 = 1.1 с у
`Edit` — любой таймаут либо режет живых, либо пропускает ждущих. Признак не
временной, а устройственный: имя инструмента. Отсюда `ask-pending` — вызван
инструмент, который по построению ждёт человека.

Порог тишины 90 с не выдуман: пауза между репликой человека и ответом модели
даёт **p99 = 61.5 с** на 16 317 наблюдениях, то есть порог промахивается на
0.4% настоящих раздумий. Поэтому `working` протухает в `idle` («молчит»), а
`waiting` не протухает никогда: агент, закончивший ход, ждёт человека и через
три часа, и гасить эту строку значит прятать единственный случай, ради которого
в трей смотрят.

Заодно всплыло продолжение находки 2.1 про белый список точек входа: на диске
появились `sdk-ts` (6 живых сессий из 20) и `sdk-cli` (305 записей), и обе
схлопывались в `unknown` — снова выглядело свойством данных, а не отставшим
списком.

**2.3 закрыт.** Темп — `packages/core/src/live/rate.ts`, прогноз —
`query/limits.ts`. Обе цифры оценочные и помечены оценкой.

У темпа всё враньё прячется в знаменателе, поэтому правил два. Окно усреднения
обрезается возрастом сессии, а моложе минуты темп не считается вовсе: сессия
возрастом в секунду с запросом на 200k при делении на её возраст даёт 12M/мин.
И единица та же, что у числа рядом, — сумма всех четырёх видов токенов: темп в
одной валюте рядом с расходом в другой не даёт вывести из них третье.

У прогноза потолка в токенах нет ни у одного провайдера: Codex сообщает только
процент, у Claude потолок задаётся руками и до 1.9 бесполезен. Зато процент
привязывается к нашему замеру — если за окно мы насчитали `W` токенов, а
провайдер говорит «израсходовано `p`%», то цена процента равна `W / p`, и
остаток выражается в тех же токенах. Единица при делении сокращается, поэтому
взвешивать `cache_read` не нужно, и прогноз работает у Codex уже сейчас.
Допущение ровно одно и оно названо: доля видов токенов в хвостовом окне та же,
что за всё окно лимита. Где процента нет — прогноза нет тоже, и сегодня это все
окна Claude.

Две проверки в пробе пришлось переписать после того, как мутации их не уронили,
и обе были неверны по существу, а не по форме. Первая сравнивала распределение
исходов и потому не видела `tool_use`, принятый за конец ответа, — то есть не
ловила ошибку, от которой каждый работающий агент зовёт человека к машине.
Вторая проверяла обратную связь темпа и времени до упора в одном направлении,
считая, что у короткого окна усреднения темп выше; на живых данных он как раз
ниже, потому что жгли раньше. Порядок тут не задан вовсе, и правильное
выражение — знак произведения разностей.

Сверка предсказания с логом заодно вскрыла три класса, которые предсказать
нельзя в принципе и которые поэтому из неё исключены с названной причиной:
запись внутри одного ответа API (общий `requestId`, `stop_reason` стоит на
каждой строке), прерывание человеком и две его реплики подряд. Без этих
исключений проба показывала 220 «ошибок», ни одна из которых ошибкой не была.

**Бриф 2.5 написан** — [`roadmap/2.5-popup.md`](roadmap/2.5-popup.md). Туда же
уехал третий известный долг: `apps/desktop/src/renderer/format.ts` со вшитым
`en-US` заменяется единым форматтером, берущим `ui.locale`, иначе десктоп и CLI
показывают разные числа на одной машине.

**Объём 2.5 поднят с M до L, и название этапа обманывает.** Вёрстка попапа —
меньшая его часть: в `apps/desktop/` сегодня только рендерер, а main-процесса,
окна, бандлера, точки монтирования и пакета `electron` нет вовсе. Витрину 2.4
физически негде посмотреть, контракт IPC из 0.4 не исполнялся ни разу. Поэтому
порядок работ обратный ожидаемому: сначала приложение запускается, потом
получает живые данные, и только потом красится по макету.

**2.4 закрыт, и это первый этап не от Codex** — делал локальный GLM, целиком
сам, без делегирования. Рендерер живёт в `apps/desktop/src/renderer/`, Electron
не поднят: окно, трей и IPC — это 2.5. Приёмка числовая, как и задумано:
`apps/desktop/test/tokens.test.ts` парсит `:root` прямо из макета и сверяет все
24 переменные, отступы каждого компонента сверяются с его блоком раздела 0,
цвета — только через `var()`, типографика — из пяти ступеней. Проверено
мутациями: сдвиг последней цифры токена, `gap: 7` и литерал `#ff8800` дают
красное. Шрифты IBM Plex лежат локально шестью `woff2` — Electron за вёрсткой в
сеть не ходит.

Одна правка после ревью, и она нового класса. Исполнитель нашёл расхождение
между макетом и правилом «отступы только 4/8/12/20/32» из
[`design-implementation.md`](roadmap/design-implementation.md) — и починил
макет: 10 → 8, 3 → 4, асимметричный `padding:8px 10px` схлопнул в один, а потом
закрепил это собственным тестом, так что вернуть значения макета стало нельзя.
Расхождение он честно описал в отчёте, но всё равно сделал. Прав при этом был
макет: набор 4/8/12/20/32 — про ритм списка, а не про внутренности компонентов,
и документ теперь это говорит прямо. Вывод для следующих брифов: слабой модели
мало написать «остановись и сообщи» — она сообщает **и** делает, поэтому нужен
явный запрет менять эталон и требование оставить расхождение в коде нетронутым.

**2.5 закрыт, и главный его результат — факт, а не вёрстка: `node:sqlite`
работает в main-процессе Electron 43 без единого флага** (Electron 43.3.0,
Node 24.18.1 внутри). Открытый вопрос про `better-sqlite3` под Electron
закрывается: нативный модуль не нужен, `electron-rebuild` в упаковку (M5) не
поедет.

Приложение поднято целиком: main на обычном `tsc` (бандлером не прогоняется —
иначе `node:sqlite` и домашние каталоги пришлось бы чинить настройками сборки),
preload отдельной сборкой в CommonJS (при `sandbox: true` ESM в preload не
поддерживается вовсе), рендерер на Vite с двумя точками входа. Витрина 2.4
наконец открывается: `npm run -w @agentmeter/desktop gallery`.

Смоук — `scripts/probe/desktop-smoke.ts`, шесть проверок на **собранном**
приложении. Две из них не про Electron, а про саму проверку: сборка не должна
отставать от исходников (иначе смоук доказывает работу кода, которого уже нет),
и смоук обязан **падать** под `ELECTRON_RUN_AS_NODE=1`.

Эта переменная — находка этапа и стоила двух заходов исполнителя. В окружении
разработчика она выставлена (наследуется от хоста VS Code), и под ней бинарник
Electron стартует обычной нодой: `require('electron')` отдаёт строку с путём,
`app` равен `undefined`. Опасно не падение, а зелёный результат — `node:sqlite`
есть и в простой ноде, снимок соберётся, код выхода будет 0, и «доказательство
работы Electron» окажется доказательством работы ноды. Поэтому проверка
подлинности стоит первой строкой main, а запуск идёт через
`apps/desktop/scripts/launch.js`, который переменную снимает.

**Контракт 0.4 пришлось чинить, и нашёл дырку исполнитель.** Довод «рендерер не
считает» упирался в три места, все три — недосмотр владельца: `DayTotals` не
давал готовой суммы (число в подвале пришлось бы складывать в окне из четырёх
полей, выводя пятую точность из четырёх), а `TraySnapshot.limits` был объявлен
голым `LimitWindow[]` и терял оба поля, которые `limitsReport` уже считает, —
`unavailableReason` и `forecast`. Без первого проверка «незнание не показано
нулём» была невыполнима в принципе: показать причину нечем. Исправлено —
`DayTotals.total`, `limits: LimitReportRow[]`, тот же тип у `limits:get`;
фикстура повторяла ту же ошибку и обновлена вместе с контрактом.

Приёмка — 44 теста рендерера, и каждая проверка показана красной мутацией
продуктового кода: потерянный и лишний канал, потерянный канал в клиенте
preload, ноль вместо незнания, полоса на неизвестном проценте, оценка без
штриховки, точное число со знаком `≈`, `gap:7`, `fontSize:14`, ссылка на Google
Fonts в собранном бандле, форматтер с зашитой локалью.

**Две мои проверки мутацию пережили, и обе были неверны по существу.** Первая
требовала «нет ширины 0%», а неизвестный процент, дошедший до стиля, даёт не
ноль, а `width:null%` — полоса рисуется, проверка молчит. Вторая, переписанная
на «заливок столько же, сколько известных окон, и все ненулевые», пропускала
константу в ширине. Итоговая сверяет ширины с процентами поимённо: показать
чужой процент — ровно то, ради чего затевался 1.8.

Долг форматтера закрыт: единый `packages/core/src/format/tokens.ts`, обе точки
входа передают ему `ui.locale`, суффикс тысяч строчный как в макете. CLI
приведён к макету, и маска в его снапшот-тесте тоже — она матчила `[KMB]` и
после смены регистра тихо перестала маскировать суффикс.

**Расхождений с макетом не правил ни одного.** Попап свёрстан своими числами
(`gap:9`, полоса 6px, кегли 9/10/12.5), и это не ошибка макета, а другой
контекст: в коде разница живёт необязательным параметром с дефолтом раздела 0,
в приёмке — вторым диапазоном строк у компонента. Таблица блоков —
[`roadmap/design-implementation.md`](roadmap/design-implementation.md).

Про исполнителя. Три захода, ноль строк продуктового кода, но ни одной подмены:
движок не менял, эталон не трогал, за собой убирал, и третья остановка нашла
настоящую дырку в контракте. Две первые — среда: в песочнице Codex нет сети за
бинарником Electron, а сам Electron в ней падает в `SIGABRT` (Chromium пишет
вне рабочего каталога). Ошибка постановки моя: правило «остановись и сообщи»
было написано слишком широко и накрыло ограничение среды, которое к решениям
владельца отношения не имеет.

## Как делегируется

Через скилл `delegate-to-codex`. Задача уходит, только если в бриф влезли четыре
вещи. Пример для 1.1, остальные пишутся по тому же шаблону:

> **Файлы:** создать `packages/core/src/sources/claude/*`. Не трогать ничего
> за пределами этой папки, `types.ts` в том числе.
> **Контракт:** типы из `packages/core/src/sources/types.ts` заданы, менять их нельзя.
> **Критерий:** `npm test -w packages/core -- claude` зелёный, все 8 фикстур
> из `fixtures/claude/` разбираются без исключений.
> **Данные:** `fixtures/claude/`, ожидаемый разбор в `fixtures/claude/*.expected.json`.

Без четвёртого пункта Codex сочиняет данные и уверенно рапортует об успехе,
поэтому фикстуры (0.6) делаю сам и до всех парсеров.

**Не делегируется:** контракты M0, модель атрибуции, калибровка лимитов,
`verify`, платформенная возня с треем, рекомендации по экономии. В первых
четырёх ошибка тихая — тест зелёный, а цифра врёт. В остальных критерий —
«выглядит правильно на трёх ОС».

Резать при этом надо **внутри этапа, а не по этапам** — так сделан 1.6. Модель
и эталон с посчитанным вручную ответом пишу сам, реализацию с тестами и пробой
отдаю. Пометка «сам» в таблице относится к решению, а не к объёму кода. Проверка
того стоит: эталон, написанный до кода, остановил исполнителя на ошибке в моей
же арифметике вместо того, чтобы подогнать реализацию под неё.
